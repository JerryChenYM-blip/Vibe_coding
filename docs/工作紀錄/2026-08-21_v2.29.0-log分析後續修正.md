# 2026-08-21 — v2.29.0：log 分析後續修正（砍零使用功能 + 修時長 bug + 字典）

## 1. TL;DR

派 4 個 Sonnet sub-agent 分角度掃 30MB log + 738 筆歷史，總管親自複核後執行三件事：

1. **砍掉三個月零使用的功能**（-157 行）：email / note / code_comment 三個情境模式、
   翻英文 / 條列 / 會議紀錄三個 Voice Shortcuts。
2. **修好長錄音時長記錄錯誤**（`gui.py:3017`）——**738 筆歷史裡有 371 筆（50.3%）
   時長是錯的**，這個欄位壞掉污染了本次分析本身。
3. **字典 +13 條修正規則 +8 個術語**，並發現**只有前 30 個術語真的會生效**
   （`prompts.py:135` 寫死 `terms[:30]`），使用者的 73 個術語有 43 個一直是白列的。

## 2. 策略決策

### 2.1 為什麼敢砍那六個功能

不是「感覺沒人用」，是資料庫欄位級證據：`preset_used` 在 738 筆三個月資料裡
**只出現過 `default`(725) 與 `chat`(13)**，其餘六個一次都沒有。

根因不是使用者沒發現，是**綁錯 App**：這些模式綁的是 Mail / Notes / Xcode，
但實際 `target_app` 分布是 Claude 68%、Edge 9.8%、LINE 6.1%、Codex 4.6%，
Notes/Word/Xcode 合計不到 2%。

**更關鍵的是：情境模式只有在 AI 潤飾開著時才有作用**，而使用者的
`polish_backend = off`——整層是睡著的。所以也**刻意不做**「Claude 專屬模式」
（68% 的使用場景目前無人服務），因為在潤飾重新變得夠快、值得打開之前，
做了也是睡著的。這是刻意不做，不是忘了做。

### 2.2 時長 bug：一個壞掉的欄位污染了分析本身

這件事的教訓比 bug 本身重要。四個 agent 裡有三個用到 `duration_s` 欄位，
**只有一個去質疑它**。總管一度根據它下結論「八成錄音短於 10 秒，所以切塊
優化不值得做」，直到第四個 agent 指出欄位壞掉才發現整個結論建立在髒資料上。

`duration_s` 用「字數 ÷ 秒數」交叉檢驗，738 筆有 371 筆（50.3%）落在
物理不可能的區間（每秒 >12 字；中文正常語速 4~5 字），最誇張一筆
**6.9 秒配 4612 字＝每秒 666 字**。

**修正後的判斷**：切塊只在錄音 ≥12 秒時啟動，既然至少 50.3% 明顯被切過塊，
真實情況是「至少一半的錄音會用到切塊」，不是先前誤判的兩成。
**但真實的錄音長度分布目前仍不可知**——結構化 log 裡有 `audio.duration_s` 的
只有 10 筆，樣本太小。正確做法是等修好後累積新資料再量,不是拿另一個
不可靠的估算去換掉它。

### 2.3 字典只有前 30 個術語生效

`prompts.py:135` 是 `"、".join(terms[:30])`——**順序即優先序**。使用者有 73 個
術語，第 31 個之後（各種銀行、政府機關名稱）從來沒有送進辨識模型。

而佔著前 30 名的有 7 個近乎沒在講：Claude API(0 次)、Claude Opus(0)、Azure(3)、
MLX(4)、Claude Sonnet(4)，以及兩個公司／金融機構名稱（各 1~3 次）。
已把它們往後移，換上語料高頻詞。

注意：`Claude Sonnet` 被降級是刻意的——使用者回報過「Claude Design 常被辨識成
Claude Sonnet」，把錯誤答案留在辨識先驗裡等於在強化它。

- 字典規則用 App 自己的 `dictionary.apply_corrections()` 實測 6 個案例全對，
  含兩個「必須不被改動」的保護案例（跟正確性、麥克風裝置）
- 字典規則寫入前先在 738 筆語料上回放：**修正 19 筆、誤傷 0 筆**

### ⚠️ 已知測試缺口（誠實列出）

**時長 bug 沒有回歸測試。** 那段合併邏輯埋在 `_run_transcription` 深處，要測得把
整條管線（背景執行緒、transcriber、狀態機）都架起來，成本遠高於修改本身。
目前只有「改動前後各跑一次完整測試」確認沒弄壞既有行為，**沒有任何測試會擋住
未來有人把 `duration_seconds=self._full_audio_s or ...` 改回去**。

## 7. 下次 session 接手指南

- **要改字典** → 記得 `prompts.py:135` 只取前 30 個術語，**加在後面等於沒加**。
  改 corrections 時注意它是 `str.replace` 純字串取代、沒有正則，
  所以「跟正→更正」這種規則必須錨定（否則「跟正確性」會變「更正確性」）。
  **任何新規則都要先在 `history.db` 全語料回放驗證誤傷再寫入**——
  專案有前例：一條沒驗證的規則把「已經準備」改成「已精準備」，整個功能被停用。
- **要分析 log** → `~/.whisper_app/logs/` 只保留約 11 天且滾動加速中。
  另有長期保存的 `~/.whisper_app/transcribe_log.jsonl`（32MB，結構化）。
  **已知污染日：2026-08-02（10 小時意外錄音）、2026-08-05（97 分鐘），
  以及 2026-08-14 18:08 ~ 08-15 04:27 的測試汙染**（該時窗的 ERROR/WARNING
  幾乎全是 `pytest` 寫進來的假錯誤，特徵是 traceback 含 `unittest/mock`、
  `RuntimeError: boom`、`key='fake_key'`）。分析前務必先排除。
- **看到整齊的數字要先驗真偽**。本次兩度中招：一批「各 51 次」的錯誤其實是
  pytest 跑了 51 輪；先前也有 82 筆「看門狗觸發」被誤判成使用者忘記關錄音。
  判準：數值過於整齊、集中在同一時窗、參數像測試值 → 先讀 traceback 再下結論。
