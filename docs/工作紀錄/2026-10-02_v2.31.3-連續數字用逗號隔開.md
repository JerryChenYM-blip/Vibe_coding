# 2026-10-02 — v2.31.3：連續唸數字時用逗號隔開（蘋果辨識）

## 1. TL;DR

使用者回報：用蘋果辨識連續唸數字時，數字之間沒有逗號，甚至整串黏成一個數字。

| 唸法 | 修之前 | 修之後 |
|---|---|---|
| 83、122、26、55（停 0.3 秒） | `831222655` | `83，122，26，55` |
| 561、60、390、450（停 1.5 秒） | `56160390450` | `561，60，390，450` |
| 同上（停 3 秒） | `56160 390450` | `561，60，390，450` |
| 訂單編號是 83、122、26，請幫我查 | — | `訂單編號是 83，122，26，請幫我查一下` |
| 電話、「一千二百萬零三百」、一般句子 | — | **完全不受影響**，也不會變慢 |

以上皆為合成語音＋背景雜音（RMS 0.005）實測。**真人錄音尚未驗證**，要使用者實際唸幾串數字確認。

## 2. 根因：三種黏法，兩種是蘋果的、一種是我們的

用一支實驗版 helper 把蘋果「切好的每一段」與「每個字的時間」原樣吐出來，才分清楚：

1. **蘋果自己用空格隔開**：`83 122 26 55`——它有分，只是用空格不用逗號。
2. **我們接段落時黏住（我們的錯）**：停頓夠久時，蘋果切成 `561｜60｜390｜450` 四段，
   v2.31.0 的 helper 直接相接 → `56160 390450`。
3. **蘋果在同一段裡就黏住**：停頓 0.3～1.5 秒時，蘋果把整串寫成 `56160390450`，
   而且它回報的每字時間資訊（`audioTimeRange`）也把整串當成**同一塊**（0.00–8.16 秒）
   ——**蘋果內部根本沒記錄停頓**，光看它的輸出無論如何都分不回來。

**對照組 Qwen3**：同樣的錄音，Qwen3 會用「，」分開（但寫成國字「八十三，一百二十二」），
1.5 秒那組漏切一處。這解釋了使用者的體感：以前用 Qwen3 數字會分開，換蘋果就黏住。

## 3. 修法

| 狀況 | 修法 | 位置 |
|---|---|---|
| ② 接縫黏住 | helper 改交出原始段落 `parts`；Python 重接：數字接數字補「，」、英數接英數補空格、中文直接相接 | `_join_apple_parts` |
| ① 空格隔開 | 「數字 空格 數字」→「數字，數字」 | `_SPACE_BETWEEN_NUMBERS` |
| ③ 同段黏住 | 偵測到 5 位以上的數字串 → 用 App 既有的 Silero 人聲偵測照停頓切開 → 一次把所有小段送進 helper 重問 → 依重問結果在原文補逗號 | `_repair_glued_digits` + `_insert_digit_separators` |

另：helper 新增「`--audio` 可以給很多次」的批次模式。三小段一次送 0.43 秒、分三次送 0.62 秒。

### 安全鎖：只補逗號、不改數字

切開重問的結果**只用來決定逗號插哪裡**，原文的字一律保留（不拿重問的整句取代原文——
切開後每段上下文變少，非數字部分可能反而聽得比較差）。

而且原文每一串數字都必須**逐字等於**重問結果裡連續幾組接起來，才准拆。對不上就從那裡之後
全部保留原樣。所以切錯（例如把「一千二百萬」切成兩半）不會改出錯的數字——數字會對不上、
那串就不動。4 位以下的串（多半是年份 2026）就算被切開也不拆。

### 為什麼門檻是 5 位

實測黏住的例子最短 5 位（`12226`）。門檻只決定「要不要試著切開重問」，不決定插不插逗號，
所以寬一點不會改錯字，只會讓少數本來就是長數字的句子多一次人聲偵測（只切出一段就直接放棄，幾乎不花時間）。

### 人聲偵測參數（參數掃描結果）

| 停頓至少／前後留／門檻 | 0.3 秒停頓 | 加雜音 | 對照組 |
|---|---|---|---|
| 200ms／80ms／0.35 | 只分出一半 | ✗ 分不開 | ✓ |
| **120ms／40ms／0.35（採用）** | ✓ | ✓ | ✓ |
| 100ms／30ms／0.5 | ✗ 乾淨音檔反而分不開 | ✓ | ✓ |

`say` 指令的「停 300ms」實測空檔只有 0.24～0.27 秒，所以要用 120ms 才抓得到。
對照組：電話 `0912345678`、「一千二百萬零三百」、逐字唸的帳號「一二三四五六七八九」，三個都沒被切。

## 5. 意外發現：「賬」字（已用換字規則修，不在版控）

**先更正一個錯誤判斷。** 開發時用合成語音測「帳號是一二三…」，輸出是「賬號」，當時判斷成
「帳號會被寫成賬號、要加規則」。**錯了**：那次測試直接呼叫 `_transcribe_apple`，
跳過了 `transcribe()` 裡的換字規則那一步；使用者字典**早就有**「賬號→帳號」「賬戶→帳戶」兩條，
App 裡實際貼出去的是對的。教訓：**驗輸出時要確認走的是哪一段管線**，後端直呼叫不含換字規則。

但查歷史時發現真正的問題更大：opencc 台灣轉換把「账」轉成「賬」，台灣慣用「帳」。
逐詞補的兩條規則蓋不到賬單、結賬、出賬、呆賬、賬務、賬密、流水賬……
全部歷史 4,843 段共 36 處「賬」，**最近一次是 10-02 的「賬單」**。

**2026-10-03 經使用者同意**，在 `~/.whisper_app/dictionary.json` 加一條單字規則 `賬 → 帳`
（備份：`~/.whisper_app/dictionary.json.bak-2026-10-03`；對備份 diff 為純新增，188 → 189 條）。

單字規則不違反 `_FANJIAN_FIXES` 旁的「禁單字」鐵律：那條是因為「隻」也是量詞（一隻美股），
單字換成「只」會改錯；「賬」只有帳目一個意思、台灣一律寫「帳」，往這個方向換不會產生錯字。
影子驗證 36 處全部該改、0 誤傷；本來就寫對的「蚊帳」「帳篷」不受影響（規則只認「賬」）。

## 6. 留給下一個人的坑

1. **真人錄音還沒驗。** 所有實測都是 `say` 合成語音（加了白雜音）。真人停頓長短不一、背景有
   人聲或冷氣聲，人聲偵測的表現可能不同。先看使用者實際使用後的紀錄：搜尋
   `apple digit repair` 這行 log，`runs_split` 是補了幾串、`segments` 是切成幾段
   （**log 只記數量不記內容**——數字可能是帳號、電話、金額）。
2. **已知取捨：英數詞後面接數字也會被換成逗號。**「Qwen3 0.6B」會變「Qwen3，0.6B」。
   使用者全部歷史裡這種寫法一次都沒出現過，所以接受；有測試記錄這件事
   （`test_已知取捨_英數詞後面接數字也會被換成逗號`）。
3. **新編譯的 helper 要先跟系統登記一次才能用模型。** 每次重新編譯（`build.sh`）或換一支
   新的執行檔，`AssetInventory` 都會回「supported（沒裝）」，要帶 `--allow-download` 跑一次
   （幾乎是瞬間，不是真的下載）。App 暖機時會自動做，但手動測試時會撞到。
4. **Qwen3 本來就會分開數字，這次只修蘋果。** Qwen3 寫國字（八十三），蘋果寫阿拉伯數字（83）。
5. **超過 60 秒的單段錄音不做切開重問**（`_DIGIT_REPAIR_MAX_AUDIO_S`）。串流模式下每段約 8～12 秒，
   正常碰不到；碰到的是不走串流的超長錄音。
