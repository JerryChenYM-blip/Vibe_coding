# 2026-10-06 — v2.32.3：啟動變慢的根因（麥克風模式「語音突顯」）與背景準備麥克風

## 1. TL;DR

- **根因**：macOS 27 上，Whisper Pro 的**麥克風模式（控制中心）是「語音突顯」**時，App 身分每向系統查一次音訊裝置屬性要 0.05～0.3 秒
  （系統每次都重新協商語音突顯處理）。錄音元件（sounddevice）一載入就要查約 126 次 → **9.8～15.4 秒**，每次插拔重掃 **9.5 秒**
- 改「標準」：載入 0.19～0.24 秒、重掃 0.01 秒；實際啟動 **20.8 秒 → 4.7 秒**（2026-10-06 16:20 實測）
- 使用者想**開語音突顯又要快**，所以 v2.32.3 把「掃全部裝置」移出主執行緒：
  - 錄音元件改在視窗出現後於背景載入
  - 插拔重掃改在背景
  - 設定視窗不再當場重掃
  - 準備中按熱鍵 → 提示「麥克風準備中」，不卡畫面
- 開麥克風本身不受影響：語音突顯那一週按熱鍵到麥克風開好，中位數 152 ms（升級前 134 ms）

## 2. 怎麼查到的（給下一個遇到怪慢的人）

| 步驟 | 結果 |
|---|---|
| 啟動時間歷史 | 9/25 前 6～7 秒；**9/30 起** 13～21 秒；macOS 27.0.1 是 9/30 12:33 裝的 |
| 終端機跑同一份程式 | import 全部 1.7 秒 → 程式本身不慢，只有「當 App 開」才慢 |
| `open --env PYTHONPROFILEIMPORTTIME=1 ~/Applications/WhisperPro.app` | 結果在 `~/.whisper_app/launcher_stderr.log`：`sounddevice` 單一模組 **15.41 秒** |
| 量測工具：`open -n --env PYTHONPATH=<hook> ...` 掛 `sitecustomize.py`，用 App 身分只量一件事就結束 | 不碰使用者正在用的 App；載入 9.8 秒、重掃 9.5 秒 |
| 逐個裝置、逐個屬性計時（ctypes 直呼 CoreAudio） | **每一次查詢都慢**，不是某個裝置慢 → 問題在「系統怎麼對待這個 App」 |
| 系統紀錄（要用 `/usr/bin/log`；zsh 的 `log` 指令名稱被 shell 佔走了） | coreaudiod 58 次 `audio_dsp_manager ... semantics = voice isolation ... Activation` |
| 用 App 身分讀 `AVCaptureDevice.preferredMicrophoneMode` | **2（語音突顯）**；終端機是 0（標準） |
| 使用者在控制中心改「標準」後重量 | 載入 0.2 秒、重掃 0.01 秒 → **因果確定** |

網路上另一個語音轉文字 App（MacParakeet，GitHub issue #1102，2026-09-19，macOS 27.0）的系統紀錄也有「替這個 App 啟用語音突顯」（`Voice isolation DSP is available for client…`、`Enabling HAL Voice Isolation support`），但它回報的是麥克風反覆重開，不是查詢變慢；我們看到的 `audio_dsp_manager … Activation` 那行**網路上找不到別人回報過**（2026-10-08 查證更正：原本寫「完全相同」是錯的）。
沒有找到官方可以讓 App 關掉麥克風模式的設定（Info.plist／entitlement）；只有使用者能在控制中心改，而且要錄音中才看得到。

## 3. 改了什麼（v2.32.3）

| 位置 | 改法 |
|---|---|
| `recorder.py` | Mac 上不在 import 時載入 sounddevice；`ensure_sounddevice()`（加鎖、只做一次、失敗不重試）、`sounddevice_ready()`／`sounddevice_failed()`；Windows 照舊 import 時載入。`read_microphone_mode()` 讀麥克風模式 |
| `gui.AppWindow._start_audio` 等 | 視窗出現後在背景載入；完成後套用設定的麥克風、補做載入期間的插拔；記 `AUDIO: ready=… in Xs (mic_mode=…)` 與 `audio_ready` 事件，超過 5 秒寫警告說明原因 |
| `gui._transition_to_recording` | 還沒載入或正在重掃 → 提示「麥克風準備中」並留在閒置（重掃時 `start()` 要等鎖，會卡主執行緒） |
| `gui._handle_device_change` | 重掃改在背景；重掃中的多次變動合併成結束後再掃一次 |
| 設定視窗 | 不再當場重掃；麥克風還沒準備好時保留並預設選使用者設定的那支（避免一按儲存就被洗成系統預設） |
| `main.check_dependencies` | sounddevice 用 `find_spec` 確認有裝，不載入（原本在主執行緒、開視窗前載入） |

### 4.1 審查（Sonnet × 3：並行與執行緒、行為退步、模擬量測）後修正

| 問題 | 處理 |
|---|---|
| 背景重掃那 10 秒 PortAudio 是「未初始化」：主執行緒查裝置拿到空清單（實測 72%），偶爾讀到已釋放記憶體；這時開設定按儲存會把使用者的麥克風洗成系統預設 | 重掃握 `_pa_lock`；查裝置拿不到鎖就回上一份清單（`_device_cache`），不等；設定視窗在重掃中／清單空時也保留使用者那支 |
| 背景還在 PortAudio 裡時結束 App，Python 拆模組會閃退（模擬 80 次 34 次） | `recorder._on_exit`：最多等 2 秒，還在忙就 `os._exit(0)`；sounddevice 自己的收尾改由我們在確認沒人用之後呼叫 |
| 「麥克風準備中」只在主視窗提示，使用者在別的 App 看不到，像熱鍵壞了 | 同時用錄音小窗 `show_warning` 提示 |
| 元件載好到套用設定的麥克風之間約 1 秒，按熱鍵會用系統預設錄 | 改看 `_audio_ready`（套用完才設） |
| PyObjC `loadBundle` 讀麥克風模式時握 GIL，畫面頓 0.75～1.4 秒 | 改 ctypes 直接呼叫 Objective-C runtime（App 身分實測 0.016 秒） |
| 錄音中的插拔被丟掉、清單一直停在舊的 | 記著，回到閒置補做 |
| 背景執行緒在主迴圈開始前 `after()` 會漏接 | 背景載入排進主迴圈才起跑 |
| 重掃卡死時一直說「過幾秒再按」 | 超過 30 秒改說「麥克風清單更新卡住了，請重開 App」 |

### 4.2 真機第一次驗收（2026-10-06 18:42，語音突顯、插著 EarPods）後再修

| 發現 | 原因 | 處理 |
|---|---|---|
| 視窗 17 秒才出現 | 登記「裝置變動通知」（CoreAudio listener）也是跟系統音訊服務打交道，在主執行緒卡 13.7 秒 | 挪到背景、排在載入之後（`_start_device_monitor`） |
| 準備好後馬上錄音，開麥克風 8.6 秒（畫面卡住） | **系統調整期**：PortAudio 掃完裝置後，系統還要約 17 秒在背景把語音突顯調整好，這段時間開麥克風 3～7 秒 | `recorder.wait_until_settled()`：每 0.3 秒問一次預設麥克風取樣率（不開麥克風），連續兩次 < 20 ms 才算好；載入後與每次重掃後都要等 |

量測（App 身分、語音突顯，2026-10-06 晚上）：

| 條件 | 開麥克風 |
|---|---|
| 插著 EarPods、準備好後馬上開（主執行緒／背景準備都一樣） | 2.7～10.5 秒 |
| 拔掉 EarPods、準備好後馬上開 | 0.05～6.8 秒（越後面越快） |
| 準備好後等 20 秒再開 | 0.07～0.18 秒 |
| 實際流程：載入 15.6 秒 → 等調整 16.5 秒 → 馬上開 | **0.05～0.14 秒** |

輕量查詢與開麥克風同步：調整期間 80～200 ms／3～4.5 秒，調整好之後 0～2 ms／0.06～0.1 秒。

### 4.3 只有影響到正在用的麥克風才重掃（使用者要求，2026-10-07）

- 每次載入／重掃（含等系統調整）之後，`recorder.snapshot_coreaudio()` 記下：系統預設麥克風的 AudioDeviceID、
  每支收音裝置「名字 → AudioDeviceID」
- 裝置變動時（背景）`device_change_affects_us()` 只問一兩個問題：
  - 指定了麥克風：那支的 AudioDeviceID 還活著（`livn`）就不影響；上次不在、這次插回來了才算影響
  - 用系統預設：預設麥克風的 AudioDeviceID 有沒有換
  - 問不到、沒記下狀態、Windows：一律當作受影響（照原本重掃）
- 不受影響：不重掃，但仍等系統調整（沒在調整約 0.05 秒），並記 `mic_device_change_skipped`；設定視窗打開時若有這種變動，背景補一次強制重掃
- 實測（App 身分、語音突顯、已調整好）：記下狀態 15 ms；判斷 0.01 ms（指定麥克風）／0.79 ms（系統預設）

### 4.4 審查（Sonnet × 3，只重掃受影響那部分）後修正

| 問題 | 處理 |
|---|---|
| 狀態在「重掃＋等調整（約 17 秒）」之後才記：這段時間的變動被當成本來就這樣，之後比對永遠看不出 PortAudio 清單過時，可能錄錯麥克風（三位都抓到） | 掃完**馬上**記；等調整好之後再用 `portaudio_view_consistent()` 直接拿 PortAudio 清單跟系統比，對不上就再強制掃一次（只核對一層，免得對不上的機器一直重掃） |
| 備援重掃（麥克風打不開時）只有一條路會把指定麥克風的編號對回來；之後的變動被判定不影響、沒人修，模擬出錄到 BlackHole | 備援重掃後一律依名字對回編號（不在就清掉）；重掃後舊狀態作廢，下次變動一律當作受影響 |
| 打開設定強制重掃：語音突顯時擋熱鍵 27 秒、結果又來不及更新設定視窗，還會跟音量表同時動 PortAudio | 設定視窗不重掃，改背景向系統要最新麥克風名字補進選單；選了 PortAudio 還沒掃到的那支並儲存時才在背景重掃；重掃中先不開音量表 |
| 設定改回「系統預設」時沒清掉舊名字（改版前就有），判斷時照舊名字那支看 | 一起清掉 |
| 沒監聽「預設麥克風換了」：插耳機後預設晚一點才換就漏掉 | 也監聽 `dIn ` |
| 關 App 的同時背景剛好在登記監聽，監聽可能殘留 | 登記與移除用同一把鎖，關掉之後不准再登記 |
| 等調整時第一次問不到就放行（預設麥克風剛被拔時可能正在調整） | 連續三次問不到才放棄 |
| 兩支同名麥克風時判斷可能看錯那一支 | **不修**：要有兩支同名硬體；最壞是開麥克風失敗→走備援，不會靜靜錄錯 |

App 身分、語音突顯實測：掃完馬上記狀態 0.47 秒（調整期間）；調整好之後判斷＋核對 12～16 ms。

## 5. 留給下一個人的坑

- **語音突顯的實際代價**：開 App 後約 **30 秒**麥克風才能用（載入 12～16 秒＋調整 16～17 秒），系統行為、程式縮不短。
  裝置變動若影響到正在用的麥克風（被拔掉、預設換了），也要再約 27 秒（重掃 10＋調整 17）；不影響的（大多數）不用等。
  這段時間畫面正常、按熱鍵會提示「準備中」。標準模式都不到 1 秒
- 設定視窗的麥克風選單合併了「PortAudio 掃到的」和「系統現在有的」；選了 PortAudio 還沒掃到的那支，儲存後要等背景重掃（語音突顯約 27 秒）才能用它錄音

- 語音突顯開著時，**剛開 App 的頭 10～15 秒麥克風還在背景準備**，這段時間按熱鍵只會提示「準備中」。這是系統行為，程式只能避開不能變快
- **裝置變動很頻繁**：日誌顯示每天約 25 次（10/3 有 65 次），多半不是人為插拔，裝置編號在 4↔5 之間跳，像是某個裝置自己上下線
  （推斷是 iPhone 接續互通麥克風）。語音突顯時每次之後約 10 秒按熱鍵會提示「準備中」；改版前同樣情況是整個 App 凍住 10 秒。
  下一步優化：只有影響到正在用的麥克風時才重掃 PortAudio（其他變動只更新清單、不重掃）；或使用者在 iPhone 關掉「接續互通相機」
- 麥克風打不開時的備援（`recorder._open_with_fallbacks`）仍會在主執行緒重掃，語音突顯時會卡約 10 秒；這條是失敗路徑、很少走到，這次沒改
- `main.check_dependencies` 還在主執行緒 import faster_whisper（約 1.3 秒），跟這次無關，沒動（2026-10-05 優化策略 R3）
- 量測工具與實驗腳本在 session scratchpad（`bench/`），不進版控；做法見 §2，要重做時照抄
- 辨識品質：語音突顯會先幫聲音降噪，標準模式給的是原始聲音，兩者對辨識的影響**沒量過**

- 第二次（2026-10-07 01:07，登記監聽挪到背景後）：視窗 **5.3 秒**出現（第一次 17 秒）

  → 「等系統調整」用的輕量探測（查預設麥克風的取樣率）判斷太早，探測快了不代表開麥克風快。這個缺口 v2.32.3 **沒有修**，見 §7

## 7. 研究：語音突顯開著，能不能視窗一開就能錄（2026-10-08，只量測、沒改 App）

量測方式同 §2（App 身分、短命程序、不碰使用者開著的 App）；麥克風只算音量確認有聲音，不存、不留內容。
每項只量 1～2 次，數字有起伏，看量級不看小數。

**結論：不是資料結構或程式效能的問題。** 同一份程式在標準模式 0.2 秒載完；慢在語音突顯時系統每回答一次要 0.05～0.3 秒。
能改的是「少問」：

| 實驗 | 結果 |
|---|---|
| 新程序只查預設麥克風需要的 8 項（不載 PortAudio） | 共 **0.59 秒**（PortAudio 全面掃描要 10～15 秒） |
| 用系統的 AudioQueue 只開預設麥克風（ctypes，16 kHz float32 單聲道，回呼走 AudioQueue 自己的執行緒） | 程序啟動後 **1.9～2.6 秒**就收到聲音（實際 App 視窗 3.55 秒才出現） |
| 同上，但開完就關、之後隔幾秒再開 | 程序啟動後**約 30 秒內**每次開都要 1～4 秒（12 秒時 4.05、20 秒時 3.22、25 秒時 1.94）；**30 秒後** 0.05 秒 |
| 第一次開麥克風延到 15 秒才開（之前完全沒開過） | 仍要 1.76 秒，25 秒再開 1.94 秒 → 慢的期間是「程序啟動後約 30 秒」，不是「第一次開之後」 |
| **啟動就開著、一直開到 30 秒才關** | 啟動後 2.06 秒收到聲音、30 秒內聲音不斷（最長間隔 0.25 秒）；關掉後 33／40／50 秒再開都 **0.06～0.07 秒** |
| 啟動就開著、只開到 15 秒 | 18 秒、25 秒再開仍要約 1 秒，35 秒才 0.06 秒 → 要撐到約 30 秒 |
| 混合：AudioQueue 開著的同時背景載 PortAudio | PortAudio 載入仍 **12.38 秒**（開著麥克風不會讓查詢變快）；AudioQueue 開著時 PortAudio 再開同一支麥克風 3 秒內**收不到聲音**；AudioQueue 關掉後（33、40 秒）PortAudio 開 0.04 秒 |

**可行做法（推斷，未實作）**：Mac 上錄音改走「只開一支麥克風」的系統錄音方式（AudioQueue 或 AVAudioEngine），不再載 PortAudio；
App 一啟動就在背景把麥克風開著，撐過頭 30 秒（這段時間按熱鍵直接從開著的麥克風取聲音，立刻能錄），30 秒後沒在錄就關掉，之後每次按 0.06 秒開好。

代價與要注意的：
- 每次開 App，選單列的**橘色麥克風燈會亮約 30 秒**（聲音沒錄下來，但使用者看得到）
- 要重寫 Mac 的錄音部分：指定麥克風（AudioQueue 用裝置 UID 設 `kAudioQueueProperty_CurrentDevice`）、打不開時的備援、設定視窗的音量表、裝置清單（改用 CoreAudio 只查名字）、邊錄邊辨識的分段，都要搬過去；Windows 不動
- 不能兩套並用：AudioQueue 開著時 PortAudio 開同一支麥克風收不到聲音
- 實驗用 3 個 0.05 秒的緩衝，開著期間最長間隔 0.25 秒，正式版要加大緩衝，否則可能掉音
- 這些都只在語音突顯量過；標準模式下 AudioQueue 的表現**沒量**（推斷一樣快）

**網路查證（Sonnet，2026-10-08，來源附在各點）**
