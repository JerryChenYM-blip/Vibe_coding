# 2026-09-25 — v2.31.2：版本號補改 + 「關於」顯示更新日期

## 1. TL;DR

- 版本號從 **2.30.0 → 2.31.2**（中間的 v2.31.0、v2.31.1 程式碼早已在 main 上，只是版本號沒跟著改）
- 設定 →「關於」的版本號底下多一行 **「2026-09-25 更新」**
- 新增「版本號查不到日期就紅燈」的測試，並把「每次更新都改版本號＋日期」寫進 `CLAUDE.md` §12-8

## 2. 為什麼

使用者在「關於」看到 **2.30.0**，不確定蘋果辨識那些修正有沒有更新到。

實際上程式碼都在（main = `26004f9`，蘋果後端、標點空格、簡轉繁三個 commit 都在），
但 `_version.py` 一直停在 2.30.0——commit 標題寫了 v2.31.0、v2.31.1，版本號本身沒改。

**這是 `_version.py` 第三次被記錄到漏改**：v2.3.0→v2.4.0 連 4 版、v2.6.0→v2.11.0 連 6 版、
這次 v2.31.0/v2.31.1。前兩次的對策（集中成單一來源、`build_app.sh` 比對 git tag）都擋不住
「根本沒去改」這種失誤。

使用者同時提出：版本號底下加更新日期，光看版本號判斷不出是不是最新版。

## 3. 設計決策：為什麼用「版本 → 日期」對照表，不用兩個獨立常數

```python
__version__ = "2.31.2"
_RELEASE_DATES = {"2.31.2": "2026-09-25"}
__release_date__ = _RELEASE_DATES.get(__version__, "")
```

兩個獨立常數（`__version__` + `__release_date__ = "..."`）的失敗模式是：**只改版本號、忘了改日期**，
日期停在舊的，但畫面看起來完全正常，沒有任何檢查抓得到。

對照表的話，新版本號查不到日期 → 空字串 → `tests/test_version.py` 紅燈。

查不到時刻意回空字串、不拋 `KeyError`：忘了填日期不該讓 App 開不起來。「關於」頁面遇到空字串
就不顯示那一行（不顯示「更新日期：未知」——那是開發端的錯，不該讓使用者看到）。

`__version__` 那一行格式**不能改**：`build_app.sh:29` 是用 grep + sed 從原始碼撈版本字串，
不是 import。測試 `test_打包腳本讀得出版本號` 直接跑那一行一模一樣的指令來守這件事。

| 項目 | 方式 | 結果 |

| 查不到日期會紅燈 | 在暫存副本把版本改成 2.31.3、不加日期，跑測試 | ✓ 紅燈，訊息寫明要加哪一行 |

沒有重開使用者正在用的 App——怕打斷他。使用者要**重開 App** 才會在「關於」看到新版號。

## 6. 意外發現（沒修）

**git tag 從 v2.27.0 之後就沒再打了**（v2.28.0、v2.29.0、v2.30.0、v2.31.x 都沒有 tag）。
`_version.py` 的發版鐵律第 5 步是 `git tag`，這一步已經斷了好幾版。

影響：`build_app.sh:36-56` 會比對 `_version.py` 與最新 tag，不一致就跳「版本不一致，Continue anyway?」
要人按 y 才能打包——現在每次打包都會跳。

**刻意沒補**：打 tag、推 tag 是發版決策，而且要不要回頭補 2.28～2.30 的 tag 需要使用者決定。

## 7. 留給下一個人的坑

1. **漏改版本號沒有任何自動化擋得住。** 測試只能擋「改了版本號但忘了日期」，擋不了「根本沒改版本號」。
   目前唯一的防線是 `CLAUDE.md` §12-8 的規則。
2. **`.app` 的 Info.plist 版本號（Finder「取得資訊」看到的）還是 2.30.0**，要重跑 `bash build_app.sh`
   才會更新。「關於」頁面不受影響——它是執行時直接讀 `_version.py`。
3. **不要用 `screencapture -R` 截區域來驗設定視窗。** 這次試過，視窗被壓在使用者的瀏覽器後面，
   拍到的是使用者當下的螢幕內容（已當場刪除）。要驗「字有沒有出現、位置對不對」，
   直接走訪 widget 樹讀 `cget("text")` 與 `winfo_rootx/rooty`——比截圖可靠，也不會拍到不該拍的東西。
