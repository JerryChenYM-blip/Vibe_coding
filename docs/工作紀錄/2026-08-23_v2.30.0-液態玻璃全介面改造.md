# 2026-08-23 — v2.30.0：液態玻璃全介面改造

## 1. TL;DR

參考另一個產品（MeetingNotes）的玻璃設計稿，把 Whisper Pro 全介面改成液態玻璃風格。
**核心限制**：tkinter 沒有 alpha 合成、沒有模糊、沒有 backdrop-filter。解法沿用
`waveform_render.py` 已驗證的路線——PIL 離屏渲染成靜態圖再貼上 Canvas。

新增 `glass_render.py`（雙級玻璃引擎）。九個區塊按「能不能做真玻璃」分兩級處理：

| 真玻璃 | 顏色匹配（誠實標記，不是真玻璃）|
|---|---|
| 迷你懸浮條、狀態槽、底列 | 頂列、歷史清單/搜尋列、設定視窗（搜尋列/側欄/底列）|

波形（大/小、深淺兩套）淺色改深墨語言：平常不變色，只有削波才轉紅——
修正了「一直喊狼來了」的舊語意。

**過程中發現並修正兩個真 bug**（都是總管親自驗證抓到，不是 agent 自陳）：
1. 歷史清單一度誤標「真玻璃」，實測證實是 100% 永遠不可見的死程式碼
2. 整合測試才炸出的屬性初始化順序 bug（見 §5）

197 個測試全程維持不變。

## 2. 策略決策

### 2.1 核心技術限制：customtkinter 的 transparent 不是真透明

在動手前先讀了 customtkinter 原始碼驗證：

```python
# ctk_base_class.py: _detect_color_of_master()
if master_widget.cget("fg_color") != "transparent":
    return master_widget.cget("fg_color")
elif ...:
    return self._detect_color_of_master(master_widget.master.master.master)
```

`fg_color="transparent"` 只是「往上找祖先的實色來平塗」，**不是真的透明合成**。
CTk 元件疊在裸 `tk.Canvas` 上也一樣——會取 `master.cget("bg")` 一塊實色。

**結論：要玻璃，那塊區域就得整個交給 canvas 畫。** 這條限制決定了整輪工作的分法。

### 2.2 風險分級：呼叫點數量決定做真玻璃還是顏色匹配

每個區塊動手前先數清楚「這個元件在全檔案裡被 `.configure()` 幾次」：

| 區塊 | 元件數 | 呼叫點 | 做法 |
|---|---|---|---|
| 迷你懸浮條 | 全視窗即玻璃本體 | 0（獨立視窗）| 真玻璃 |
| 狀態槽 | 1（電平表）| 少量、集中 | 真玻璃 |
| 底列 | 2 | 5 | 真玻璃（複製鈕仍是 CTkButton，見 §2.3）|
| **頂列** | 6 | **30** | 顏色匹配 |
| 歷史清單/搜尋列 | 多個 CTk 控制項 | 中 | 顏色匹配 |
| 設定視窗三塊 | 側欄按鈕等 | 3（側欄）| 顏色匹配 |

30 個呼叫點散在錄音狀態切換、Ollama 輪詢、暖機進度等十幾處。全部重寫成 canvas
繪製的風險，比照歷史清單那次全部重寫出過的「文字正常但整列點不到」P1 bug。
**改用折衷：內部元件與呼叫點完全不動，只把外框背景色從固定值換成「離屏算一張
玻璃圖、取樣中心點顏色」**，視覺上跟真玻璃區塊協調，不強求物理真實。

判準寫進了後續每一輪的 prompt 裡：**只有講得出「玻璃會從哪個具體區域露出來」
才做真玻璃**（迷你條整個視窗都是玻璃本體、狀態槽的電平表比外層矮 8pt 留了
pady margin）。講不出具體露出範圍的，一律做顏色匹配，不准假設「應該會透」。

### 2.3 內容區一律不玻璃化

底列的複製鈕、歷史視窗右側詳細面板、設定視窗六個功能頁、主視窗轉錄流本文——
全部刻意維持實色底。理由是同一條原則：**玻璃鋪在「介面」上，不鋪在「內容」上**
（抄自參考設計 `材質提案.html` 的原話）。讀寫內容的區域需要穩定的對比度，
半透明疊加只適合裝飾性的邊框／工具列。

### 2.4 波形色彩語言：從「一直變色」改成「只有削波才變色」

淺色主題波形原本用 `energy_color(v)`——每根 bar 依自己的高度查色溫。頻譜對稱化
之後，中央的 bar 本來就最高，結果普通音量中間就整片泛橘、看起來像一直在警告，
真正的削波反而不明顯（第一版做完存 PNG 才發現這個問題）。

改成參考設計的做法：主體 `#4a4a52` 深墨、軌道 `#d8d8de` 淺灰、**只有音量真的
超過門檻（0.78）才泛暖、削波才轉紅**。深色主題維持原本的色溫斜坡不動——
深底上那組色彩是讀得出來的能量指示，沒有同樣的問題。

## 3. 修正前 vs 修正後

### 3.1 玻璃疊放結構（以狀態槽為例，真玻璃可行的情況）

```
[狀態槽 40pt 高]
┌─────────────────────────────────────┐
│ ┌───────────────────────────────┐   │ ← 玻璃背景 canvas
│ │         (4px 邊界露出)          │   │    640×40，place() 置中
│ │  ┌───────────────────────┐    │   │
│ │  │   電平表 640×32         │    │   │ ← _chamber，bg=取樣色
│ │  └───────────────────────┘    │   │
│ └───────────────────────────────┘   │
└─────────────────────────────────────┘
   electric meter 比外層矮 8pt（pady=4×2）
   → 玻璃在這 8pt margin 裡「真的」露出
```

### 3.2 歷史清單那次的錯誤與修正

```
[誤標「真玻璃」的版本]              [修正後]
list_canvas (340×524)              list_canvas (340×524)
  ↑ 完全蓋住                          bg = 取樣色 #f9f9fa
list_glass_canvas (340×524)        （玻璃 canvas 已移除）
  ↑ 100% 永遠看不到
  （雖然真的算了一張玻璃圖）

隔離實驗證實：兩個同尺寸 canvas 疊放，
上層 bg 永遠完全遮住下層，
不因內容多寡、捲動位置而改變。
```

### 3.3 波形色彩語言

```
[修正前] color = energy_color(bar高度)      [修正後] color = f(整體音量 level)
─────────────────────────────              ─────────────────────────────
每根 bar 各自查色 → 中央必泛橘              全條同色，只有 level > 0.78 才泛暖
「有點大聲」與「破音」分不出來               削波時整條轉紅，一眼看到
```

## 5. 總管驗收（親自做、非採信 agent 回報）

這輪工作全部由 sub-agent（Sonnet）分區塊執行，每個區塊做完總管都親自驗證，
不採信 agent 的自我報告。抓到的問題：

### 5.1 歷史清單「真玻璃」宣稱是假的

Agent 回報「真玻璃，只是大部分被清單內容蓋住，捲動條收起或內容少時會露出」。
總管用最小化隔離實驗直接測 Tk 語意（兩個同尺寸 canvas，一紅一藍疊放，截圖看
紅色會不會透出）：

```
中心像素 = 藍色（上層）    左上角 = 藍色（上層）
```

**紅色在任何位置都沒有透出來。** 不是「偶爾」，是 Tk 的固定行為——canvas 的
`bg` 是整塊 widget 矩形的不透明底色，跟內容多寡完全無關。那段程式碼在算一張
12-14ms 的玻璃圖，但畫面上永遠不會有任何一個像素被看到，而且留了一段寫著
「這仍然算真玻璃」的錯誤註解。已移除死程式碼、修正註解、把這個教訓寫進了
後續（設定視窗）的任務指示裡，agent 之後確實直接沿用、沒有重蹈覆轍。

### 5.2 整合測試才炸出的初始化順序 bug（本輪唯一真正的程式邏輯 bug）

單獨測歷史視窗、單獨測主視窗都是綠的。**只有把六個視窗在同一個 session 裡
串起來跑**才炸出：

```
AttributeError: 'HistoryWindow' object has no attribute '_list_glass_size'
```

根因：`self._list_glass_size = None` 這行初始化，寫在 `_list_canvas.bind("<Configure>", ...)`
之後（因為那是總管自己動刀移除死玻璃 canvas 時，把初始化行留在原本的位置沒跟著
挪）。但 `<Configure>` 事件可能在 bind 呼叫之後、後面那行程式碼執行之前就先被
Tk 觸發一次——這正是「以為程式碼由上到下線性執行」在 Tk 事件迴圈裡不成立的
經典案例，這個專案已經在別的地方（`_on_list_canvas_configure`）踩過同一類坑，
這次是總管自己在修正上一個 bug 時又introduce了一次。已修正：初始化提前到
bind 呼叫之前，並在整合測試裡重跑驗證，六個視窗同時存在無例外。

**教訓：任何時候搬動或新增一段初始化程式碼，都要重新確認它跟同一個物件上
其他 `<Configure>`／`<Button-1>` 等事件綁定的相對順序，不能只看「有沒有加」。**

### 5.3 波形色彩門檻的兩次迭代

第一版用「bar 高度比例」判斷要不要上色，結果普通音量（0.45）中央就整片泛橘
——因為頻譜對稱化後中央 bar 本來就最高，跟音量無關。存 PNG 打開看才發現。
改成用「整體音量 level」驅動門檻，重新渲染驗證：0.15/0.45/0.70 全維持深墨、
0.85 才泛暖、0.95 削波才整條轉紅。

### 5.4 淺色玻璃在近白底上本來就讀不出來

第一輪原型玻璃疊在純漸層底上完全看不出效果——這不是 PIL 的限制，CSS 也一樣，
玻璃的原理是「透出並模糊底下的東西」，底下是白的透出來還是白的。解法沿用
參考設計的做法：鋪兩團很大、很淡、中心在畫布外的徑向光暈（`radial_backdrop()`），
濃度只有 .24～.46，淡到不會讓頁面看起來彩色，但足夠讓玻璃有東西可以透。

## 7. 下次 session 接手指南

### 想改玻璃質感

進入點是 `glass_render.py` 的 `GlassSpec` 與 `draw_glass()`。改完
**一定要存 PNG 打開看**——本輪至少三個問題（歷史清單死程式碼、波形泛橘、
外緣線畫成硬邊）全部是看圖才發現，讀程式碼一個都看不出來。

### 想加新的玻璃區塊

先問自己一句話：**「這塊玻璃會從哪個具體像素區域露出來？」** 答不出來就不要
做真玻璃，做顏色匹配（離屏算圖、取樣中心點、設進 `fg_color`／`bg`）。範本：
- 真玻璃：`_build_status_slot()`（gui.py，有 pady margin 真的會露出）
- 顏色匹配：`_build_topbar_v2()` 開頭（gui.py，30 呼叫點零風險）

### 想確認一個元件的呼叫點風險

```bash
grep -c "self\.\_元件名\." gui.py
```
超過個位數就要考慮顏色匹配而非全部重寫成 canvas。

### 任何新增/搬動初始化程式碼的地方

如果那個物件上還綁著 `<Configure>` 或其他事件，**確認初始化一定排在 bind 之前**。
這個坑本輪踩過一次（§5.2），不是理論案例。

### 整合測試不能省

單獨驗證每個區塊是綠的不代表全部一起跑也是綠的。改動任何一個共用視窗前，
先把六個視窗在同一個 Python session 裡建立一次（本次交接紀錄的驗證腳本可以
直接參考），確認沒有互相干擾。
