# 2026-09-17 — v2.31.0：蘋果原生語音辨識後端（第四種 backend）

## 1. TL;DR

設定選單多一個模型選項 **`apple-speech`**，直接用 macOS 26 內建的語音辨識引擎，
不載任何本地權重。

| 項目 | 數字 | 怎麼量的 |
|---|---|---|
| 6.5 秒音訊 | **約 330 ms**（穩定後全程） | 合成語音、連跑 4 次 |
| 57 秒音訊 | **約 1,537 ms**，未被截斷 | 合成語音、單次 |
| 對照：現況中位數 | **1,775 ms** | `transcribe_log.jsonl` 近 12 天 562 筆 |
| 本 App 記憶體佔用 | **0**（模型在作業系統裡） | 沒有 lazy load、`unload()` 不需處理 |

**準確度完全沒有測過。** 上面所有數字都是用 `say` 合成語音量的，只證明「管線會動、
速度快」，不能拿來說「比較準」。準確度要等 T02 的真人素材（見 §7）。

## 2. 策略決策

### 2.1 為什麼要多寫一支 Swift 程式，不直接用 PyObjC

macOS 26 的新引擎（`SpeechAnalyzer` / `SpeechTranscriber` / `DictationTranscriber`）
**是 Swift-only，Apple 沒有橋接給 Objective-C runtime**，所以 PyObjC 完全看不到：

```python
import objc
objc.loadBundle('Speech', globals(), bundle_path='/System/Library/Frameworks/Speech.framework')
objc.lookUpClass('SpeechAnalyzer')     # → nosuchclass_error
objc.lookUpClass('SpeechTranscriber')  # → nosuchclass_error
```

對照 SDK 的 `Speech.swiftinterface`（742 行）：這些型別宣告成 `final class` / `actor`，
全檔只有 19 處 `@objc`，而且幾乎都是 `deinit`，不是真的 API 表面。

### 2.2 為什麼不用舊的 `SFSpeechRecognizer`（PyObjC 叫得到的那個）

舊 API 確實可以從 Python 直接呼叫，而且實測 `zh-TW` 支援離線
（`supportsOnDeviceRecognition == True`）。**但 Apple 文件載明單次辨識約有 1 分鐘上限，
超過會被系統截斷。** 這個 App 常有超過一分鐘的錄音，尾巴被默默砍掉是最糟的失敗模式
——使用者不會發現。

> ⚠️ **不要因為「PyObjC 比較省事」就把這條改回舊 API。** 那會讓長錄音默默掉尾。

### 2.3 為什麼選單裡只放 `speech`、不放 `dictation`

helper 兩種引擎都實作了，但只有 `speech` 進選單。實測同一段音訊：

| 引擎 | 輸出 |
|---|---|
| `speech` | 今天我們來測試蘋果的語音辨試引擎 ，看看它能不能正確辨識中文。 |
| `dictation` | 今天我們來測試蘋果的語音辨識引擎看看他能不能正確辨識中文 |

**`dictation` 沒有標點。** 這個 App 的輸出是直接貼進游標處，沒有標點幾乎不能用。
（有趣的是 `dictation` 那次「辨識」是對的、`speech` 錯成「辨試」——單一樣本，不能下結論。）

`dictation` 引擎保留在 helper 裡（`--engine dictation`）供日後比較，
但刻意不放進 `MODEL_INFO`，免得使用者選了才發現沒標點。

### 2.4 helper 放哪裡：沿用既有的「相對於原始碼檔案」慣例

`_APPLE_HELPER_PATH` 用 `os.path.dirname(os.path.abspath(__file__))` 算，
也就是相對於 `transcriber.py` 自己的位置，**跟行程的工作目錄無關**——
跟 `splash.py` / `app_icon.py` 定位資源的作法一致。所以 helper **不進 `.app` bundle**，
`build_app.sh` 一行都不用改。

（初版註解誤寫成「靠 launcher 先 cd 回專案目錄」，已於審查後更正：
`build_app.sh:148` 的 `cd` 是為了 `main.py` 與 `PYTHONPATH`，跟這條路徑無關。）

## 4. 意外發現

### 4.1 不需要任何權限彈窗，也不需要 Info.plist 的 usage description

原本預期要在 `build_app.sh` 兩份 plist 各加一條 `NSSpeechRecognitionUsageDescription`
（舊 API 少了這個 key 呼叫 `requestAuthorization` 會直接當掉）。

**實測：新引擎從裸終端機、沒有 bundle、沒有授權，直接就能跑。**
`SFSpeechRecognizer.authorizationStatus()` 至今仍是 `0`（尚未詢問）。
→ `build_app.sh` 完全不用動。

### 4.2 `AssetInventory.status` 與 `installedLocales` 會互相矛盾

第一次探測時 `installedLocales` 已經含 `zh_TW`，但 `status(forModules:)` 回 `supported`
（＝支援但沒裝）。真的跑一次 `downloadAndInstall()` 之後才變 `installed`
——而且**幾乎是瞬間完成**，代表那一步實際上只是註冊／保留，不是真的下載幾百 MB。

判準：**看 `status(forModules:)`，不要看 `installedLocales`。** 後者會給你假的安心感。

### 4.3 純靜音會產生幻覺，跟 Whisper 一樣

`tests/golden_set/001_silence.wav`（1.5 秒靜音）→ 輸出 `"you"`。
純正弦波 → 空字串（正確）。

**「換成蘋果就不會有幻覺」是錯的預期。** 既有的幻覺過濾器仍然必要。

**已驗證擋得住**：同樣兩個檔走完整 `transcribe()`，最終輸出都是「（未偵測到語音內容）」
——既有的靜音閘／幻覺過濾在使用者看到之前就攔下了。這條不必再擔心。

### 4.4 第一次呼叫多花的 1.9 秒不是蘋果的，是我們自己的

完整 `transcribe()` 第一次 2,456 ms、純後端只有 329 ms。差額是 **Silero VAD 模型載入**
（T01〔A〕的量測程式與既有靜音閘共用）。第二次之後前後處理只剩 **19–62 ms**。

這件事在 Whisper/Qwen 時代看不出來（相對於 1.8 秒的推論不明顯），
換到 330 ms 的後端才浮上檯面。**以後要再壓延遲，前處理就是下一個標的。**

### 4.5 `contextualStrings` 接上了，但測不出效果

拿 `speech` 引擎誤判的「辨試」當自然實驗，把「辨識」「語音辨識」餵進 `contextualStrings`
再跑同一個音檔——**輸出一字不變**。

可能是合成語音太乾淨、模型太有把握，也可能是用法還不對。**目前沒有證據說這個機制有效。**

> **2026-09-25 更新：真實使用確認沒用。** 見 §8.3——「叡揚」「Opus」「Fable」都在字典裡、
> 也確實傳進 `contextualStrings`，蘋果照樣寫成「瑞陽」「Obos」「Fabe5」。

## 6. 對抗式審查抓到的東西（全部已修）

初版寫完後派了三個角度（正確性／隱私安全／系統整合）各自獨立審查。
**抓到 3 個 major，全部是真的，全部是初版的錯。** 這一節留著是因為這三個坑
都很容易在下一個後端重犯。

### 6.1 暖機寫死 zh-TW → 非中文使用者進入永久死循環

暖機用 `_APPLE_DEFAULT_LOCALE`、轉錄用 `_apple_locale_for(language)`。
使用者把語言設成 English：轉錄要 `en-US` → 沒裝 → 顯示「請重開 App 讓它背景下載」
→ 重開後暖機裝的還是繁中 → **永遠修不好，而且錯誤訊息還在指導使用者做無效的事**。

**修法**：`warmup(model_size, language=None)` 加參數，`gui.py` 啟動暖機時傳
`self.cfg.get_whisper_language()`；`_warmup_apple` 的探測與下載都改用同一個 locale。

> 教訓：**「暖機時用的參數」與「實際執行時用的參數」不一致，是會生出死循環的。**
> 蘋果的模型是一個語言一份，這點跟 Whisper / Qwen3 的多語言單一模型不同。

### 6.2 失敗訊息會被當成逐字稿，自動貼進使用者的輸入框

`gui.py` 判斷「這次結果有沒有效」用的是**硬編碼的兩句話白名單**。我新增了 4 種
失敗訊息，一句都不在裡面 → 這些中文錯誤訊息會被 ⌘V 貼進使用者當下的輸入框
（Slack、信件都有可能）、寫進歷史紀錄、還送去 Ollama 潤飾。

而且 `helper_missing` 是**重新 clone 之後 100% 會發生**的——`bin/` 被 gitignore、
`build_app.sh` 也不會編譯 helper。

**修法**：新增 `transcriber.is_system_message()`，用「單行且整句被全形括號包住」
判斷，取代兩處硬編碼清單（`valid` 與 `is_fail`），並移除變成孤兒的 `_FAIL_TEXTS`。

> 順帶修掉一個既有的洞：Qwen3 的失敗訊息本來也不在白名單裡，同樣會被貼出去。
> **白名單擋不住「有人新增一種失敗而忘了同步清單」——閘不能靠記性。**

### 6.3 閒置保活每 90 秒重開一支下載程序

`gui.py` 的 keepalive 每 90 秒呼叫 `warmup()` 保溫 MLX 權重。蘋果後端被我接進
`warmup()` 之後，等於每 90 秒開一支子程序；模型還沒裝好時更糟——`--allow-download`
的 timeout 是 600 秒，600 ÷ 90 ≈ **最多疊 7 支下載程序同時對外連線**，而且只要一天
裝不起來就永遠不停。對一個主打「100% 本地」的 App，這是使用者不知情的持續對外請求。

**修法**：keepalive 遇到蘋果後端直接 `return`——它的模型在作業系統裡，
本 process 沒有任何東西需要保溫。（`return` 安全：重新排程寫在 `finally` 裡。）

### 6.4 其他已修

| 問題 | 修法 |
|---|---|
| helper 回 `ok:false` 時正常回傳 → audit 記成 `error=None` 的**成功**紀錄 | 改成拋 `AppleSTTError`，分派區接住並把錯誤碼寫進 audit |
| 0 影格的 wav 會讓 helper 永遠卡住（results 串流收不到結束訊號） | Swift 端 `guard file.length > 0`；Python 端也擋一層 |

| `build.sh` 註解把路徑成立的理由寫錯（說靠 launcher 的 `cd`，實際靠 `__file__`） | 改寫註解 |

**驗證**（不是只看測試綠燈，是實際跑）：把 `_APPLE_HELPER_PATH` 指到不存在的路徑、
餵一段真的有聲音的音訊走完整 `transcribe()` →

- 使用者看到：「（找不到蘋果辨識元件、請執行 native/apple_stt/build.sh 重新編譯）」
- `is_system_message()` 判定為系統訊息 → **不會被自動貼上**
- audit JSONL 最後一筆：`backend=apple-speech, error=apple_helper_missing` → **失敗被記成失敗**
- 空 wav：離開碼 2、回 `empty_audio`（修之前是 timeout 被殺，離開碼 124）

## 8. 2026-09-25 追加：真實使用三天後的發現（v2.31.1）

使用者 9/21 晚上切到蘋果、用了整整三天（到 9/24 傍晚切回 Qwen3 0.6B），回報「潤整效果」
不如 Qwen3。這一節是用那三天的真實紀錄查出來的。

### 8.1 先釐清：使用者說的「潤整」不是 AI 潤飾

`config.json` 的 `ollama_enabled = False`，最後一次 `polish_done` 是 **2026-06-18**，
9/17 之後 49 筆歷史紀錄 `polished_text` 全是空的、每一筆 `pipeline_timing` 都是
`path=no_ai`。使用者看到的「潤整效果」其實是**蘋果辨識本身的輸出**（自帶標點、看起來整齊）。
下一個人聽到使用者說「潤飾／潤整」時，先查這個開關，不要預設 LLM 有在跑。

### 8.2 主要問題：簡轉繁錯字，是 Qwen3 的 40 倍

| 期間（真實使用） | 模型 | 有效輸出字數 | 簡轉繁錯字 | 每千字 |
|---|---|---|---|---|
| 9/18–9/21 | Qwen3 1.7B | 4,811 | 1 | 0.2 |
| 9/21–9/24 | **蘋果** | 3,938 | **32** | **8.1** |
| 9/24– | Qwen3 0.6B | 2,703 | 0 | 0.0 |

錯法都是「一個簡體字對應多個繁體字時挑錯」：只有→隻有、前面→前麵、系統→係統、
複雜→復雜、紫微斗數→紫微鬥數、表定→錶定、回來→迴來、關注→關註。

**根因是 v2.31.0 的一個錯誤判斷**：當時在 `_transcribe_apple` 寫了「刻意不套 opencc：
zh-TW 模型輸出本來就是繁體」。實際上蘋果的繁體是它自己粗轉的；Qwen3 之所以字對，
是因為它輸出簡體後走 opencc `s2twp`（看上下文的詞組表）。

**修法**（`_renormalize_apple_chinese`）：繁→簡（`t2s`，多對一、不會挑錯）→ 依使用者的
`chinese_variant` 再轉繁（與 Qwen3 同一條，含 `_apply_tw_vocab_fix`）。

**驗證**：
- 三天 116 段真實輸出走正式程式碼重放：**32 → 0**
- 44 處改動逐一人工檢查：約 38 處修正、5 處換成台灣用語（了解→瞭解、聯係→聯絡、
  打開→開啟，與 Qwen3 輸出一致）、**1 處改壞**：「電話會裏」→「電話會里」
- 另比過 `s2tw`（只換字）與 `s2t`（通用繁體）：各剩 2 個錯字、同樣有「會里」問題 → 選 `s2twp`
- 既有鐵律「禁單字」（`_FANJIAN_FIXES` 旁的註解，源自「一隻美股」誤改事件）：
