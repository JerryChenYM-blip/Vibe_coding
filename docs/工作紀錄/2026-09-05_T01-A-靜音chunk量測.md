## 做了什麼

只改 `transcriber.py` 一個檔案。在「音檔已經通過長度閘跟音量閘、要開始判斷送不送 AI 轉錄」
的那個時間點，額外算一次 Silero VAD（神經網路語音偵測）的語音統計——不管音檔幾秒都算，
因為既有的判斷閘（第 941 行）只管 4 秒以下的音檔，10-12 秒的串流 chunk 永遠繞過去，
這正是〔A〕要回答的問題。新增 4 個欄位寫進 log：語音佔比、語音段數、最長安靜間隔、
這次 Silero 到底有沒有真的跑過。順便把一個原本寫死成 `False` 的舊欄位改成記錄真實結果。

**沒有改動任何一行「要不要送 AI 轉錄」的判斷邏輯**——新的計算只負責寫進 log，
不影響任何回傳的文字內容。

**另外補了一個鎖**（詳見「意外發現 #1」）：Silero VAD 這個共用模型原本只有「載入」
被鎖保護，「使用」完全沒有——兩個背景執行緒同時問它會讓整個 App 當機，這次改動剛好
讓原本免疫這個風險的一大群音檔（10-12 秒串流 chunk）第一次暴露在這個風險裡，所以在
同一個 commit 裡把這個鎖補上（詳見下方說明；使用者已在動手前確認要一起做這件事）。

## 意外發現 ★

1. **★★ 這次改動原本會讓一大群音檔第一次暴露在一個既有的當機 bug 裡，已在同一個
   commit 修掉。** 獨立審查找到、我自己用兩組併發測試各別重現（修復前會當、修復後
   不會）：Silero VAD 這個共用模型，`_ensure_silero_vad()` 的鎖（`_silero_vad_lock`）
   只保護「載入」那一下，**真正拿去推論（`get_speech_timestamps()`）完全沒有鎖保護**。
   兩個背景執行緒同時呼叫它，會讓整個 Python 行程直接當掉（訊號 SIGTRAP / exit code
   133，崩潰堆疊在 PyTorch 的 C++ 卷積層內部）——**這是改動前就存在的舊缺陷**（用只呼叫
   舊函式 `_silero_no_voice()`、完全不碰這次新增程式碼的重現腳本一樣會當機，證明跟
   這次新寫的東西無關）。

   但這次改動把曝險範圍實質擴大了：改動前，只有 **4 秒以下**的音檔會摸到 Silero
   模型（既有閘的 `duration<=4.0` 限制）；**10-12 秒的串流 chunk（也就是這個工單真正
   要處理的、佔算力 69.2% 的那一大群）改動前從來不會呼叫 Silero，完全免疫這個當機
   風險**。這次為了「不管幾秒都要量測」，讓所有音檔都會呼叫 Silero，等於把這群原本
   安全的音檔第一次暴露出來。串流架構（`gui.py` 的 `_dispatch_stream_chunk`）每個
   chunk 各開一條背景執行緒、彼此不等待，而 App 本身已知常常「塞車」（工單自己的資料
   量到一段錄音排隊等了快 24 秒），塞車時多條執行緒同時在跑的機率不低。

   **已經跟使用者確認、在同一個 commit 補上修法**：把 `_silero_vad_lock` 的保護範圍
   從「只蓋載入」擴大到「也蓋每一次 `get_speech_timestamps()` 呼叫」——兩個函式
   （`_silero_no_voice()` / `_silero_speech_stats()`）都改用 `with _silero_vad_lock:`
   包住那一行。這個鎖本身不影響任何判斷邏輯、不影響轉出來的文字，純粹讓「兩個執行緒
   同時要用這個模型」時排隊，不要同時衝進去。修完後：兩組併發壓力測試（2 條、4 條
   執行緒）都跑乾淨、不再當機；A2（golden set byte-identical）重新驗證仍然通過。

2. **工單提到的「1596 行那道閘，不知道有沒有跑」——實際比猜測的更明確，是死碼。**
   那道閘所在的函式 `transcribe_fast()`，全專案目前沒有任何地方呼叫它（唯二兩處提到
   它的地方都是「已停用」的舊註解）。串流 chunk 100% 走的是另一道閘（第 941 行、
   在 `transcribe()` 裡）。之後若有人要清理死碼，`transcribe_fast()` 可列入候選，
   但這次任務範圍不包含刪它。

3. **`tests/golden_set/` 目前只有 2 個測試案例，而且兩個都在到達 AI 轉錄之前就被
   別的閘擋掉了**——沒有任何現成測試案例真正走到「送進 AI、拿到真實轉錄結果」這條路。
   這代表 A2 的「行為零變化」驗證雖然通過，但驗證力道有限：只證明了「被擋下的案例
   輸出沒變」，沒有證明「真的送進 AI 轉錄的案例輸出沒變」。這次用合成雜音做了補充
   驗證彌補這個缺口，但那不是走 golden set 的正式流程。

4. **4 秒以下的音檔，Silero VAD 現在會被呼叫兩次**（一次新量測、一次既有的閘）。
   這是刻意的取捨，不是沒注意到——理由見下方「留給下一個人的坑 #2」。加了鎖之後，
   這兩次呼叫會排隊執行而不是真的同時衝突，多出來的等待時間是毫秒級、可忽略。

## 留給下一個人的坑 ★

1. **A1 跟真正的 A3 端到端數字都還沒有**——這次只做了機制驗證。需要真實使用滿一週後，
   回來看 `~/.whisper_app/transcribe_log.jsonl` 算新欄位覆蓋率，並比對 `breakdown.inference_ms`
   的分布，確認有沒有真的變慢超過 3%。

2. **刻意不做**：沒有把新的 `_silero_speech_stats()` 跟既有的 `_silero_no_voice()`
   合併成同一次呼叫（理論上可以省掉 4 秒以下音檔重複呼叫 Silero 的成本，大約每次
   省個位數毫秒）。**理由**：合併需要去動第 941 行那個判斷式本身——那是使用者特別
   交代「風險最高、不要碰」的地方，省下的時間遠不值得冒這個險。之後如果真的要做，
   941 行可以改成直接讀取新量測算出來的 `silero_stats["no_voice"]`，但那已經算改動
   gate 邏輯了，要照工單〔C〕的「先紅後綠」規格重新走一次驗證，不能當簡單重構處理。

   **補充**：雖然沒有合併呼叫，但為了修「意外發現 #1」那個當機 bug，這次**有**改動
   `_silero_no_voice()` 內部——加了一把鎖包住 `get_speech_timestamps()` 那一行。
   這把鎖不改變 `_silero_no_voice()` 的回傳值、不改變第 941 行判斷式的任何邏輯，
   純粹讓多執行緒同時呼叫時排隊，所以認定它不算「動到 gate 邏輯」。但如果之後有人
   純粹看 diff、看到 `_silero_no_voice()` 被改了，要知道這不是〔B〕〔C〕的範圍，
   是這次〔A〕在修一個獨立的執行緒安全問題。

   **殘留風險（很小，但誠實記錄）**：加鎖之後，如果真的有兩個以上的 chunk 執行緒
   同時想用 Silero，它們會排隊、不會再當機，但**排隊本身會讓其中一個執行緒多等一下**
   （等待時間 = 對方那次 Silero 呼叫的時間，量到大約 6-40ms，依音檔長度而定）。
   這個等待目前沒有算進 A3 的估算裡，但因為量級遠小於 ASR 推論的秒級耗時，
   實務上應該量不出差別；如果一週後真實資料顯示 `transcribe_start_ms` 有異常尖峰，
   這是一個可以排查的方向。

3. **刻意不做**：`transcribe_fast()`（見「意外發現 #1」）確認是死碼，這次沒有動它、
   也沒有幫它加上同樣的量測欄位——它現在不會被任何路徑呼叫到，加了也沒意義。

4. **`silero_max_gap_s` 的定義**：把「音檔開頭到第一段語音」跟「最後一段語音到音檔
   結尾」都算進候選間隔（不是只算語音段落彼此之間的間隔）。工單只寫「最長的無語音
   間隔」，沒有明確定義要不要含頭尾，這是我自己的判斷。做〔B〕訂門檻分析資料時，
   要知道這個欄位的精確定義是「含頭尾」，不要憑欄位名稱猜。

5. **`silero_speech_ratio` 理論上可能略微超過 1.0**——Silero 內建的語音段落
   padding（`speech_pad_ms` 預設 30ms）如果讓好幾段語音彼此靠得很近、padding 疊加，
   加總長度可能超過音檔總長。這次合成測試沒有實際觀察到，但〔B〕分析資料時如果
   看到 >1.0 的值，這是原因，不是資料算錯。
