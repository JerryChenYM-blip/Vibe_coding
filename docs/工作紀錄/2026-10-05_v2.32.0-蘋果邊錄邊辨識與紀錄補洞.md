# 2026-10-05 — v2.32.0：蘋果邊錄邊辨識 + 快速修正 + 紀錄補洞

> 依據：[優化策略-蘋果辨識-2026-10-05.md](../優化策略-蘋果辨識-2026-10-05.md)（同日的審查報告與三階段計畫）。
> 使用者指示：「三個全部都修掉」，中途追加「評估 log 機制有沒有缺失……一併統整起來」。

## 1. TL;DR

- **第一階段（快速修正）**：重複數字不再被吃掉；切到蘋果時放掉 Qwen3／Whisper 權重；拿掉已廢案的 Silero 統計；
  不潤飾時先貼上再畫畫面；視窗不在前景時重畫降到 1 秒一次；熱鍵看門狗不再洗版；紀錄的 backend 欄位寫對
- **第二階段（蘋果常駐串流）**：Swift helper 加 `--serve` 常駐模式，錄音當下每 0.1 秒把聲音餵進去，
  放開後只等引擎收尾。失敗一律退回舊的「整段送一次」
- **第三階段（先收資料）**：每次蘋果辨識完，背景再用「聽寫引擎」跑一次同一段錄音，兩份都寫進紀錄，
  到 **2026-10-19 自動停**；`compare_apple_engines.py` 負責比對。尾音等待改成「放開前已安靜就只等 0.1 秒」
- **紀錄補洞**：錄音編號終於帶得進背景執行緒；每筆紀錄帶版本號；每 5 分鐘記記憶體與 CPU；新增尾音、對照組事件

## 2. 改了什麼（含實測）

### 2.1 第一階段

| 項目 | 改法 | 驗證 |
|---|---|---|
| 重複數字被吃（000000→00） | `_dedupe_repetitive_ngrams` 的替換改成 `_dedupe_keep_numbers`：重複單位去掉空白／逗號後全是數字（含國字數字）就原樣保留 | `tests/test_v232_quick_fixes.py` 5 個保留 + 3 個照清 |
| 切到蘋果不卸載 | `warmup()` 遇到蘋果模型、且 `_model`／`_qwen3_session` 還在，就在 `_transcription_lock` 內 `unload()` | 測試確認卸載時鎖是拿著的 |
| 廢案 Silero 統計（每次 ~35 ms） | 移除 `_silero_speech_stats` 與呼叫點；`gates.silero_no_voice` 留 `False` 佔位（下游 schema 不變） | 全套測試 |
| 先貼上再畫畫面 | `_on_transcription_done` 不潤飾路徑：toast → 複製 → 貼上 → 記時間，**之後**才 `_transition_to_idle`（畫卡片、寫歷史） | 順序測試；潤飾路徑與系統訊息不貼的測試 |

| backend 欄位寫成 mlx | `_backend_for(model)` 取代 5 個早期紀錄點與 `actual_backend` 的 `BACKEND` 常數 | 測試 |

### 2.2 第二階段：常駐串流

- `native/apple_stt/AppleSTT.swift`：`--serve` 讀 stdin 一行一個 JSON（`begin`／`audio`／`end`／`cancel`／`ping`），
  回 `hello`／`ready`／`result`／`error`／`cancelled`。輸出一律 `FileHandle.standardOutput.write`
  （`print` 接到管線時是整塊緩衝，對面會一直等不到）
- `apple_stream.py`：`AppleStreamEngine`（全 App 一支，死了下次自動重開）、`AppleStreamSession`（一次錄音一個，
  錄音執行緒只丟佇列，背景執行緒負責送出）
- `recorder.py`：`set_block_listener`，即時回呼裡把每塊聲音交給 session（包 try/except，絕不能讓錄音停）
- `gui.py`：錄音開始建 session（建失敗不影響錄音）；有 session 時不切段；`_run_transcription` 先 `finish()`，
  拿不到就記 `apple_stream_fallback` 再走舊路
- 暖機時先把常駐程式開好（`_prepare_apple_extras`），第一句不用等開程式

**實測（合成語音，2026-10-05）**

| 指標 | 舊做法 | 新做法 |
|---|---|---|
| 放開後等辨識（中位數） | 468 ms | 約 170 ms（整合測 163～303 ms） |
| 錯字率 | 1.7% | 1.4% |
| 中途把 helper 砍掉 | — | 自動退回舊做法、下一次自動重開（已驗） |

### 2.3 第三階段

- **對照組**：`Transcriber.run_apple_shadow` 在貼上之後、背景跑一次 `--engine dictation`，寫 `apple_shadow` 事件
  （含辨識文字）。實測背景約 930 ms，不影響使用者等待
  - 原本設計是同一個常駐引擎同時跑兩個模組，實測讓放開後的等待多 130 ms，改成背景另跑
  - `config.apple_shadow_until = "2026-10-19"`，過期自動停；設定值寫錯也當作不跑
- **尾音等待**：放開前最後 0.5 秒 RMS < 0.001 → 只等 100 ms，否則照舊 300 ms。每次寫 `tail_padding` 事件
  （等了多久、放開後實際錄到多少、放開後的音量），用真資料檢查有沒有切掉尾字
- **比對工具**：`venv/bin/python3 compare_apple_engines.py [--show N]`，依錄音編號配對，量英文被吃比例、
  純中文差異程度、字典詞命中。`--show` 會印出句子，只看終端機、**不要貼進版控**

## 4. 意外發現

- **錄音編號消失的真正原因**是 `threading.local`：主執行緒設的值，背景執行緒永遠讀到空的。測試裡留了對照組
  （沒包裝時確實拿不到），之後誰改掉 `_with_pid` 會立刻紅燈
- **錄音看門狗依賴切段結果**：原本 `_last_voice_at` 只在每段辨識完才刷新。串流不切段之後，講 15 分鐘會被當成
  沒講話而自動停止。改成直接看最後 1 秒音量（≥ `_MIN_RMS` 0.004）；真資料：講話段音量第 10 百分位 0.0095、安靜 < 0.001
- 新編譯的 helper 對 macOS 來說是「新程式」，蘋果的語言資產要**重新登記一次**（每種引擎各跑一次 `--allow-download`）

## 5. 留給下一個人的坑

- **所有速度與準確度數字都來自合成語音**。真人錄音、10 分鐘以上長錄音的穩定性沒測
- 閒置 CPU 的改善只在隔離實驗驗過，真 App 待驗：比對 10/5 前後 `hotkey_health` 的 `cpu_s` 差值 ÷ 300 秒
- 尾音縮到 100 ms 是否切掉尾字：看 `tail_padding` 事件 `padding_ms=100` 的那幾筆，搭配使用者回報
- **10/19 之後**跑 `compare_apple_engines.py` 決定路由（例如「有英文用一般引擎、純中文用聽寫引擎」），這是第三階段還沒做完的部分
- 串流偶爾會把句號放在不同位置（跟整段送一次比），不影響字，但比對時別誤判成錯字
- 重建 helper：`bash native/apple_stt/build.sh`，之後要重新登記語言資產。**helper 執行檔不在版控**
  （`.gitignore`），換台電腦 clone 下來一定要先編譯；沒編譯不會壞，只是串流靜悄悄退回舊做法、沒有加速
- 開了 AI 潤飾就不走串流（刻意的，見 §7.1 #6）；設定檔 `apple_streaming=false` 可以整個關掉，改了要重開 App
- **既有、沒修**：切段辨識失敗的那一段會被靜悄悄變成空白（`gui.py` `_dispatch_stream_chunk` 裡
  `r.text.startswith("（")` 就當空字串），尾段失敗現在也是丟掉只寫日誌——使用者看不出少了一段。
  要修需要加「部分失敗」的提示，另開工單
- 審查員的探針程式在 10/5 約 18:05～18:09 往真實 App 日誌（`~/.whisper_app/logs/whisper_app.log`）寫進一批假的
  `chunk_cut` 等紀錄；跑 pytest 也會寫。分析那段時間的日誌時要排除
