# 2026-08-15 — v2.28.0：歷史清單 canvas 改寫 + 錄音大波形

## 1. TL;DR

三件事，都由使用者實際使用時的回饋驅動：

1. **歷史紀錄視窗左側清單捲動 lag** → 從「每列一張 CTkFrame 卡片」改成「畫在單一
   `tk.Canvas` 上的繪圖 item」。實測 **139.6ms/幀（7 FPS）→ 8.0ms（125 FPS）**，
   而且不再隨筆數變差。
2. **轉錄卡片上的複製／存檔鈕點不中** → 命中區從 28×22 放大到 33×30（面積 1.6 倍），
   原文／潤飾切換 40×20 → 44×26。根因是外層 meta 行寫死 `height=22` 又設了
   `pack_propagate(False)`，**只改按鈕尺寸不會生效**。
3. **波形「從左邊開始」** → 頻譜改成中心對稱（能量由中央往兩側擴散），並新增
   `waveform_render.py`（PIL 離屏渲染）做錄音態的大波形：真漸層、高斯輝光、
   色溫隨音量。錄音時接管轉錄流區域，停止後收回。

**主視窗那條 640×32 小電平條的顏色語意也一併修正**（見 §2.4），那是本次
對稱化改動造成的回歸。

## 2. 策略決策

### 2.1 歷史清單：為什麼是 canvas item，不是「少載一點」或「換輕量 widget」

先量再決定。三種做法實測（真實 `history.db`、視窗實際顯示在畫面內）：

| 做法 | 200 列 | 700 列 |
|---|---|---|
| CTk widget 卡片（原本） | 139.6 ms / 7 FPS | 更差 |
| 純 tk widget 卡片 | ~21 ms / 48 FPS | ~61 ms / 16 FPS |
| **單一 Canvas 繪圖 item** | **9.5 ms / 105 FPS** | **9.3 ms / 107 FPS** |

關鍵在最後一欄：canvas item 的成本**不隨筆數增加**，因為 Tk 只繪製可見範圍內的
item；embedded widget 則是每幀對每個 widget 做一次幾何處理，成本線性成長。
選前兩者都只是把問題往後推（使用者的資料庫已經 695 筆且持續成長）。

順帶記錄一個反諷：v2.26.0 的 commit 訊息寫「長度橫條用 CTkFrame 非 Canvas、
**Canvas 物件 0**」當成優化成果——但它算的是「canvas 上的繪圖項目數」，而真正
拖慢的是「canvas widget 的數量」。改用 CTkFrame 讓後者變多，方向剛好相反。
**優化前先確認自己量的是不是會痛的那個指標。**

### 2.2 大波形：為什麼「蓋住」而不是「讓位」

第一版做法是錄音時 `pack_forget()` 把轉錄流整塊拿掉、讓大波形佔住那格。
**連續踩到三個 Tk pack 的坑**：

1. `pack_forget()` 之後再 `pack()` 會排到**順序最後** → 轉錄流跑到底列後面、
   整塊往下位移 53pt（≈底列高度）。Tk 的 pack 沒有 `grid_remove()` 那種
   「隱藏但記住位置」。
2. 防重複 pack 的判斷式用 `winfo_manager()`，但 **CTkScrollableFrame 交給你的是
   「裡層」frame**，它的 `pack()`／`pack_forget()` 被覆寫成轉發給
   `_parent_frame`（customtkinter `ctk_scrollable_frame.py:285/294`），
   `winfo_manager()` 卻**沒有跟著轉發** → 問裡層永遠得到 `'canvas'`，
   判斷式永遠成立、還原那段永遠不執行。
3. 轉錄流一消失，**底列就往上遞補**到畫面頂端。

修到第三個時停下來換方向：**完全不動版面**，改成一張不透明畫布 `place()` 蓋住
外層 `_parent_frame`（`relwidth=relheight=1.0`），波形本身只佔中間
`BIG_WAVE_H`（renderer 的 `band_h` 參數）。三個坑一次消失。

> **教訓**：同一個方向連續踩三個坑，通常代表方向錯了，不是運氣差。

### 2.3 華麗版渲染：為什麼離開 tkinter Canvas

tkinter Canvas 只有實心圖元，**沒有** alpha 合成／漸層／模糊。既有的
`_draw_aperture_bars()` 已經把 Canvas 能做的做到頂（透明度用 `blend()` 線性插值
假裝、輝光用多層近似背景色暗示）。要真漸層／真輝光只能換管線。

改用 PIL 在記憶體畫好整幀再貼成 PhotoImage。**實測 1.5 ms/幀（652 FPS）**，
30 FPS 的預算是 33 ms。PIL 本來就是既有相依（`icons.py` 的圖示是純 PIL 手繪），
不增加安裝負擔。

### 2.4 色溫語意收窄（本次對稱化造成的回歸，一併修掉）

小電平條原本是 `color_fn = lambda i, v: energy_color(v)`——**每根 bar 依自己的
高度查色溫**。頻譜還是「左高右低」時，看起來像一條由左到右的漸層，還算合理；
改成中央最高之後，同一條就變成「兩端青、中間橘」的彩虹。而琥珀／橘在這套設計
裡的語意是**削波警告**，等於普通音量就在對使用者謊報破音。

改成 `energy_color(rms)`：整條同一個色溫、只有高度在動。
**顏色＝多大聲、高度＝頻譜形狀**，兩個維度不再互相汙染。大波形
（`GlowWaveRenderer`）從一開始就是這個規則，兩邊現在一致。

```
[修正前] f = i/(n-1)                     [修正後] f = |i−中央| / 中央
```

## 7. 下次 session 接手指南

### 想改波形長相

- **形狀／動態** → `waveform.py`（純函式、零相依、可單元測）。
  改 `f` 的定義會同時影響主視窗、迷你 HUD、上方細條——這是刻意的（三者是同一顆
  儀表的三種讀數）。
- **視覺質感（顏色／輝光／漸層）** → `waveform_render.py`。
  改完**一定要把 PIL Image 存成 PNG 打開看**：
  ```python
  r = GlowWaveRenderer(640, 240, 46); r.render(bars, level=0.5).save("/tmp/x.png")
  ```
  本次三個視覺 bug（白底被洗成灰、淺色主題光暈色相反轉、5 張圖其實是同一張）
  **全部是看 PNG 才發現的，讀程式碼一個都看不出來**。

### 想改歷史清單

進入點是 `HistoryWindow._render_grouped_rows()`。注意兩件事：

1. **canvas item 的 x 座標是繪製當下算死的**，不像 widget 有 `pack(fill="x")` 會
   自己跟著容器變寬。所以 `_on_list_canvas_configure` 是必要的，不是防禦性冗餘
   ——拿掉它，第一次繪製會用 `winfo_width()==1` 畫出 x = 8~−7 的卡片，
   **文字看起來正常但整列點不到**。
2. 存取 customtkinter 私有屬性（`_parent_frame` / `_parent_canvas` / `_scrollbar`）
   沿用本檔既有慣例：包 `try/except`。

### 驗證紀律（本次踩過的坑）

- **測試的輸入不要從被測資料自己推導**。本次命中測試一度「3/3 通過」，
  因為它拿 `_row_ranges` 自己存的 x 去點它自己——輸入與輸出同源，自我一致但全錯。
  改用**寫死的螢幕座標**才抓得到。
- **Tk 量測時視窗必須在畫面內且 `winfo_viewable()` 為真**，否則 macOS 跳過重繪、
  量到的是假數字（本次一度量到「24,598 FPS」）。
- 跑任何會建視窗的驗證腳本，**`HistoryStore` 一律指向暫存路徑**，
  `Config` 只用記憶體 dataclass、絕不 `.save()`。
  （前例：曾有自動化流程為了「實測」把使用者 40 個設定欄位打回出廠值。）
