# 2026-10-09 — v2.33.0：Mac 錄音改用 AudioQueue（只開一支麥克風）＋開 App 先暖機 30 秒

## 1. TL;DR

- **要解的問題**：macOS 27 上麥克風模式（控制中心）是「語音突顯」時，App 身分每向 CoreAudio 查一次屬性要 0.05～0.3 秒。
  v2.32.3 把 PortAudio（sounddevice）的初始化／重掃移到背景，但「麥克風準備中」仍要 10～30 秒、開 App 後前 30 秒開麥克風要 1～5 秒。
- **這版的做法**：Mac 不再載入 sounddevice，錄音改用系統 AudioQueue 只開「一支」麥克風；`main.py` 在 `import gui` 之前就在背景把麥克風開著，
  撐到程序啟動後 30 秒才關（暖機）。視窗出現時（約 3.5 秒）暖機已開好（實測 1.7～2.6 秒），按熱鍵直接接手、不碰硬體。
- **代價（使用者已同意）**：每次開 App，選單列橘色麥克風燈亮約 30 秒，聲音沒有錄下來。
- **Windows 完全不變**（仍用 sounddevice）；Mac 路徑以外的程式碼行為不動。
- 版本 2.33.0（`_version.py`，日期 2026-10-09）。

## 2. 實測依據（2026-10-08，App 身分、macOS 27、語音突顯；實驗程式在總監暫存區，未入版控）

| 事實 | 數字 |
|---|---|
| PortAudio 初始化掃全部裝置 | 約 126 次查詢 → 10～15 秒，沒辦法延後 |
| AudioQueue 只開預設麥克風 | 程序啟動後 1.7～2.6 秒收到聲音 |
| 程序啟動後 30 秒內開麥克風 | 1～5 秒（跟用哪種 API 無關） |
| 30 秒後開麥克風 | 0.05～0.08 秒（關 0.01 秒） |
| 啟動就開著、撐 15 秒才關 | 不夠；**撐到 30 秒**之後每次開 0.06～0.08 秒 |
| 問預設是哪支＋名字 | 2 次查詢約 0.24 秒；用名字列舉找 UID 2～3.7 秒；暖機期間背景列全部裝置約 2.5 秒 |
| 兩個 AudioQueue 同時開同一支 | 可以，兩個都收得到聲音 |
| AudioQueue 開著時 PortAudio 再開同一支 | 3 秒內收不到聲音 → **Mac 上不能兩套並用** |

## 3. 改了什麼

| 檔案 | 改動 |
|---|---|
| `mac_audio_queue.py`（新） | `AQInputStream`（ctypes 直呼 AudioToolbox：16 kHz float32 單聲道、8 個 100 ms 緩衝、UID 指定裝置、callback 例外一律吞掉、關閉中不再放回緩衝區）；CoreAudio 只讀查詢 `default_input`／`default_input_id`／`input_devices`（回 `[{"id": UID, "name": 名字}]`）；`busy_count`／`close_all` 給結束清理用。AudioToolbox 延到第一次用才載入，Windows 上 import 不會炸 |
| `recorder.py` | Mac 分支：`_start_mac`（接手暖機／暖機開啟中回 False／key 不符作廢／一般流程用 UID 開）、`_open_with_fallbacks_mac`（v2.31.4 的順序原封不動，身分換成 UID）、`stop()` 在鎖內只拆下串流、**鎖外**才關；暖機機制（`prewarm`／`release_warm`／`release_warm_if_affected`／`warm_state`／`warm_wait`／`warm_info`）；裝置清單快取（`list_devices` 在 Mac 只回快取、`refresh_devices()` 跨平台、`devices_ready()`）；`_on_exit` 也關 AudioQueue。**移除**（Mac 專用、改版後沒人用）：`wait_until_settled`、`_probe_coreaudio_ms`、`snapshot_coreaudio`、`device_change_affects_us`、`portaudio_view_consistent`、`_ca_snap`、`_ca_alive`、`_ca_default_input`、`_ca_input_devices`、`_CAAddr` 等。Windows 的 `start()`／`stop()`／`_open_with_fallbacks`／`refresh_portaudio` 照舊 |
| `main.py` | `import gui` 之前呼叫 `recorder.prewarm(config.json 的 input_device)`；只在 `__name__ == "__main__"` 做（測試 import main 不能開麥克風）；`_early_input_device()` 直接讀 json，不用 `Config.load()`（它可能搬移／改寫舊設定） |
| `gui.py` | `_transition_to_recording`：Mac 只在暖機「開啟中」擋（主視窗＋錄音小窗提示「麥克風開啟中」），不再因為裝置清單重新列舉而擋；Windows 擋門照舊。`_start_audio`／`_load_audio_in_background`／`_on_audio_ready`：Mac 不載 sounddevice，主執行緒只記名字，背景登記監聽、等暖機結果、記 `AUDIO: ready=… in X s since startup`。`_handle_device_change`：背景 `refresh_devices()`，Mac 再 `release_warm_if_affected`。`_apply_input_device_setting`：跟『上一次套用的設定值』（`_applied_input_device`）比，真的換了麥克風才作廢暖機；清單已填好找不到就照舊版只記 warning、退回系統預設（不列舉、不跳提示）（審查後改，見 §4b）。設定音量表 Mac 改用 `AQInputStream` 並在背景開、開好用鎖＋世代號碼交接。`on_close` 作廢暖機。設定視窗麥克風選單的 ready 判斷 Mac 改看「快取填好了沒」 |
| `tests/` | 新增 `test_mac_recorder.py`、`test_mac_audio_queue.py`；`conftest.py` 加「擋掉真實系統呼叫」與假 AudioQueue 環境 `mac_env`；`test_audio_background_init.py` 重寫（刪掉 PortAudio 等待／判斷影響的測試，其餘分 Windows／Mac 兩邊）；`test_mic_fallback.py`、`test_stability.py` 原本的 sounddevice 測試固定走 Windows 流程，另加 Mac UID 版 |
| `_version.py`／`CLAUDE.md` | 2.33.0；技術棧、坑 #18、§13 索引 |

## 5. 留給下一個人的坑

1. **AudioQueue 一定要在鎖外關**：`AudioQueueStop(immediate)` 會等正在跑的 callback 跑完，而 callback 要拿 `AudioRecorder._lock`（RLock，同執行緒可重入，所以單執行緒測試測不出來）。`stop()` 鎖內只把串流拆下來。測試用「換一條執行緒去搶鎖」偵測。
2. **暖機世代號碼**：暖機背景執行緒開麥克風可能要好幾秒，期間 `release_warm()`（換麥克風、裝置變動、關 App）會把世代號碼 +1；背景開好後發現不符就自己關掉、**不能先裝上去再關**（中間一瞬間按錄音會接手到將死的串流）。背景執行緒一律用傳進去的 `_WarmState` 物件，不讀全域（它活很久，期間全域可能被換）。
3. **30 秒是實測值，不是估的**：2026-10-08 用 App 身分、macOS 27、語音突顯量的（只撐 15 秒不夠）。不同 macOS 版本或麥克風模式不一定一樣；若日後別版本不需要暖機，`_WARM_HOLD_S` 改小即可。實驗程式（`bench_aq_hold*.py`）在總監暫存區、未入版控。
4. **Mac 上 PortAudio 與 AudioQueue 不能並用**（AudioQueue 開著時 PortAudio 再開同一支，3 秒內收不到聲音）。不要為了「某個功能方便」在 Mac 重新 `import sounddevice`。
5. **橘色麥克風燈 30 秒是使用者同意的代價**，不是 bug。若使用者以後反悔，退路是改回 v2.32.3 的做法（背景載入 PortAudio），或把暖機改成只在設定了語音突顯時才做（目前不判斷）。
6. **主執行緒絕不做 CoreAudio 列舉**（語音突顯時 2～4 秒）。`list_devices()` 在 Mac 只回快取；啟動初期快取是空的，`set_device_by_name` 只記名字，UID 等 `refresh_devices()` 填完才對上，或 `start()` 當場解析（慢路徑、少見）。
7. **舊測試會在 Mac 上默默開真麥克風**：改版後 Mac 的 `start()` 不走 sounddevice，原本「換掉 `sd.InputStream`」的測試若沒指定 `IS_MAC=False`，會真的開 AudioQueue（開發中有兩輪全套測試因此短暫開過麥克風，才加上 conftest 的擋門；後來審查的 mutation 又讓一個測試走到真的 `sd.InputStream`，所以再加了第二道封鎖，見第 13 條）。新測試一律用 `mac_env`；要走 Windows 流程就 `monkeypatch.setattr(recorder, "IS_MAC", False)`。
8. **`main.py` 的 prewarm 排在單一實例鎖之前**：開 App 時舊的程序還沒被殺掉就先開了麥克風（兩個程序同開一支沒問題，實測兩個 AudioQueue 同開可以）。首次安裝尚未授權麥克風時，授權視窗會比主視窗早出現。
9. **`main.check_dependencies` 仍檢查 sounddevice 有沒有裝**：Mac 現在其實用不到它，但 Windows 需要，requirements 也沒動；沒裝的話 Mac 也會被擋。
10. **跨平台函式的語意**：`_device_index` 在 Mac 是 UID 字串、Windows 是 PortAudio 編號；`_index_for_name()` 兩邊共用（名字沒改）。`refresh_devices()` 在 Windows 就是 `refresh_portaudio()`。
11. **備援路徑仍在主執行緒列舉**：麥克風打不開時走 `_open_with_fallbacks_mac`，它會呼叫 `refresh_devices()`（列舉約 2.5 秒）與 `builtin_input_device_name()`（逐一問每個裝置的連接方式），而且是在 `start()` 握著錄音鎖、主執行緒上做。只有『開麥克風失敗』才會走到，所以刻意沒搬到背景（搬了就要處理『失敗之後使用者等不等』的體驗）。審查 A 項已把常見的『設定的麥克風沒插著』從這條路徑拿掉，剩下的是真的打不開（硬體卡住、被別的 App 占用）。
12. **首次啟動的麥克風權限提示會在視窗出現前跳出**：`prewarm` 排在 `import gui` 之前，第一次安裝／被重設權限時，系統的『要使用麥克風嗎』視窗比主視窗還早。使用者沒回答前暖機大概會一直是 opening（這是推斷，沒有真機實測；`AUDIO: ready=False … 60 秒還沒好` 的 warning 就是為了讓這種情況在日誌看得到），按熱鍵會提示『麥克風開啟中』；回答之後應該就會開好。
13. **測試期間曾短暫真的開過麥克風：實作期間 2 次、審查 mutation 1 次，已加兩道封鎖**。實作期間 2 次：`tests/conftest.py` 擋掉 `mac_audio_queue._load` 之前，改版後的 Mac `start()` 不走 sounddevice，舊測試沒指定 `IS_MAC=False` 就真的開了 AudioQueue（選單列橘燈短暫亮起）。審查 mutation 1 次：第二輪審查拿掉設定音量表 Windows 分支的一個判斷，測試走到真的 `sd.InputStream`（程序還當場閃退，RC-11）。現在兩道封鎖都在 `tests/conftest.py`，每個測試自動套用：①`_never_touch_real_audio` 擋 `mac_audio_queue._load`（AudioQueue／CoreAudio）；②`_never_open_real_portaudio` 把 `sounddevice.InputStream`／`RawInputStream`／`Stream`／`RawStream` 換成會丟例外的替身（測試自己注入假的 `recorder.sd` 不受影響）。`allow_coreaudio_read` 只給只讀查詢。不要為了方便移除這些封鎖。
14. **`requested` 欄位與『名字對帳』**：設定的麥克風沒插著時，暖機開預設、`requested=名字`、`key=None`，錄音器的 `_device_name` 在啟動對帳（`_on_audio_ready`）前還是那個名字，所以 `_take_warm` 同時認 `key` 與 `requested`。對帳之後名字被清掉（只動 runtime，config 保留，下次插回來仍會用回原裝置）。若改動這段，三處要一起看：`_warm_worker`、`_take_warm`、`release_warm_if_affected`。
15. **`refresh_devices()` 在 Mac 失敗回 `None`**（Windows 仍回清單）：呼叫端一律要能接受 None；回舊快取會被當成權威清單，把使用者選的麥克風當成已移除。
16. **作廢暖機之後 30 秒內不會重新暖機**（第三輪 A3 刻意不做的另一半）：換麥克風、預設換了、要求的那支插上，都會 `release_warm()`；之後 `prewarm` 只有 `main.py` 啟動時呼叫一次。所以開 App 後 30 秒內發生作廢，下一次按錄音要在主執行緒開麥克風（實測 1～5 秒，`_start_mac` 握著錄音鎖），之後 `stop()` 才不卡（A3 已改背景關）。30 秒後這個成本降到 0.06 秒，影響只限開 App 後的前 30 秒。要補的話：`release_warm` 後判斷是否還在 30 秒內，是就背景重新 `prewarm`（要處理世代與 key 的重新決定）。
17. **設定的麥克風靠『清單更新時恢復』，不靠當下判斷**（第三輪 A2）：`start()`、`set_device_by_name()`、`_apply_device_list` 的『被拔掉』都會把 runtime 的 `_device_name` 清成 None（只動 runtime，config 保留）；`gui._apply_device_list` 在每次清單更新時，若 runtime 沒在用麥克風而 config 設定的那支在清單裡，就靜默恢復。改動任何一處清名字的邏輯時，要確認這個恢復路徑還接得上，不然會回到『一次誤判就整個執行期間錄預設』。
18. **`_take_warm` 對 `requested` 的條件看的是『清單快取』**（第三輪 A1）：`_requested_still_absent()` 要求清單已填好且那支不在才接手。清單沒填好就走一般流程（可能當場列舉）。動快取填入時機（`_warm_worker`、`refresh_devices`、`_set_mac_devices`）時，要想到這個條件。

## 6. 真機驗證清單（總監做；步驟與指令都用 App 身分）

1. 麥克風模式設「語音突顯」，冷啟動 `~/Applications/WhisperPro.app`：日誌 `AUDIO: ready=True in X s since startup` 的 X 應約 1.7～2.6；視窗一出現就按熱鍵能錄，日誌有 `RECORD: took over warm microphone`。
2. 開 App 後等 35 秒：選單列橘燈熄；再按熱鍵：日誌 `Stream active in 0.0x s (warm takeover: no…)`。
3. 設定換麥克風並儲存（30 秒內與 30 秒後各一次）、插拔耳機／iPhone 麥克風：錄音用的是對的那支，沒有「準備中」。
4. 設定視窗「錄音」頁音量表會動，離開頁面橘燈（若暖機已過）熄。
5. 關 App 後橘燈熄、不閃退（`~/.whisper_app/fault.log` 沒有新記錄）。

## 7. 沒做／刻意不做

- 沒有「暖機秒數」設定項（30 秒寫成常數＋註解）。
- Windows 完全沒動；`docs/競品拆解-Typeless-*.html` 沒動。
- 沒有判斷麥克風模式再決定要不要暖機（標準模式暖機也無害，只是橘燈多亮 30 秒）。
- 沒有 commit／push。
