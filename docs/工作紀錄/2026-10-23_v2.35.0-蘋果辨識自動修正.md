# 2026-10-23 — v2.35.0：蘋果辨識結果加「英文詞比對字典」自動修正

依據：[蘋果語音辨識原理與提升準確度研究](2026-10-23_蘋果語音辨識原理與提升準確度研究.md) §2、§7，以及總監定案的修正（拿掉 A、重寫 B）。
**未 commit**（工作目錄還有未提交的 v2.32.3～v2.34.0，這版疊在它們上面）。版本 2.35.0（`_version.py`，日期 2026-10-23）。CLAUDE.md 沒有描述到被改的行為，未更動。

## 1. TL;DR

蘋果引擎的文字在「字典 corrections 之後」多過一道修正：把拼錯的英文專有名詞（clardcode、gitub、Nervidia…）換回使用者字典裡的寫法。Qwen3／Whisper 一個字都不變。

**這一版有兩個大轉折，下一個人務必看：**

1. **原規格的 A「重新轉繁體」整段拿掉了。** 不是忘了做。
2. **B 整個重寫成「以不改錯為第一優先」。** 第一版 B 在 33 句正常英文裡改錯 19 句。

## 2. 為什麼拿掉 A（重新轉繁體）

- A 想修的錯字（錶格→表格、係統→系統、合並→合併…），**App 實際路徑上本來就有一道在修**：`_finish_apple_payload` 裡的 `_renormalize_apple_chinese`（v2.31.1，t2s 再 s2twp＋台灣用語修正），預設就開。
- 審查（robustness）實測、總監用個人測試集按 App 實際路徑重量確認：**加 A 之後錯誤數 74 → 74，沒有任何增益。**
- **更正研究報告 §7：** 報告寫的「重新轉繁體修好 13 處（錯誤率 11.6%→10.3%）」，是總監當時拿到蘋果原文、**漏算了這道既有的重整**。那 13 處在 App 裡本來就已經被既有重整修掉。
- 移除範圍：`_apple_retraditionalize`、白名單 `_APPLE_RETRAD_REASONS`／`_APPLE_RETRAD_WHITELIST`、`_OPENCC_VARIANT_MAP` 的內部名稱 `traditional_tw_chars→s2tw`、A 的測試、`_run_apple_autofix` 裡的 A、audit 的 `apple_retraditionalize` 濾鏡、日誌的「重新轉繁體換了 N 字」。有測試（`test_A_已拿掉_相關東西都不在了`）確認它們不在了。
- **不要補回來。** 如果看到蘋果文字裡還有錶格、係統，先確認是不是繞過了 `_finish_apple_payload`（例如直接呼叫 `_apple_*` 純函式），而不是缺了 A。

## 4. B 的規則與每一條擋掉的實例

第一版 B（拿字典詞比拼字距離、門檻 0.34）在 33 句正常英文裡改錯 19 句，這種錯會直接貼到使用者游標處，不能接受。現在的規則：

| # | 規則 | 擋掉的實例（第一版會錯改） |
|---|---|---|
| 1 | 比對單位＝一個英文詞，或剛好一個空格隔開的兩個英文詞 | — |
| 2 | 單位前一個或後一個字元是 `. _ - / @ :` 就整個跳過 | 網址裡 cloud→Cloud、cloud.google.com→…CRM…、cloud_run、line_number |
| 3 | 單位裡每個詞都是**正常英文字**就什麼都不做，連大小寫都不改 | fine/online/inline/lines→LINE、code→Codex、motion→Notion、clause→Claude、planter→Palantir、Cloud Code→Cloud Codex、line／notion／cloud 維持小寫 |
| 4 | 大小寫修正：正規化（小寫、只留英數）後跟字典詞完全相同、而且不是正常字 → 改字典寫法 | gpt4o→GPT4o、nvidia→NVIDIA（但 line 不變 LINE） |
| 5 | 模糊比對的目標只用「純 ASCII、正規化後 ≥ 5 字元」的字典詞 | LINE、Opus、Rust、Zoom 這種短詞不當目標（Opuz→Opus 是 0.25，會吞常見字） |
| 6 | 門檻：編輯距離 ÷ 較長長度 **≤ 0.30**（原 0.34）；最近的比第二近至少少 0.10；單位與候選都 ≥ 3 字元；**只差結尾數字或 s 不換** | GitLab→GitHub（0.33）、mini→Gemini（0.33）、Python3→Python、Qwens／Qwen→Qwen3 |
| 7 | 字表檔不存在（或太小）→ 整步跳過 B，記一次 `log_error` | 寧可不修也不要亂修 |
| 8 | 兩個詞一組：成立就整組換，同一位置不再對單字各自比對 | Clawd Code→Claude Code、clad sonet→Claude Sonnet、claud code→Claude Code（不是「Claude code」） |

**正常英文字表**：`/usr/share/dict/words`（macOS 內建 web2，約 23.6 萬字），lazy 載一次、快取成 frozenset。再加：
- **簡單字尾還原**：s、es、ed、ing、er、ly（含「去字尾補 e」「重複子音還原」）。**er／ly 的詞幹至少 5 字**——wisp+er 若算正常字，Wisper（Whisper 的拼錯）就修不到了；s／es／ed／ing 詞幹至少 3 字。
- **補充字表 `_MODERN_ENGLISH_WORDS`**：web2 是 1990 年代的字表，沒有 online、inline、email、app、login、deploy、token、cache、merge、commit、review、session、prompt、workflow、dashboard、plugin、template、mini、gitlab、llama 等。不補的話它們會進模糊比對（online/inline→LINE 就是這樣來的）。刻意**不放**字典常見專有名詞（github、claude、gemini、ollama、nvidia），它們要能做大小寫修正與被比對。

其他照原規格：只在蘋果模型、在 corrections 之後、系統訊息（「（」開頭）不處理、例外不讓轉錄失敗（`log_error("apple_english_match_failed")`）、日誌只寫 `英文比對換了 M 處`（沒換不寫，不寫任何文字）、audit `post_filter_applied` 的 `filter=apple_english_match`、`hits={原: 新}`。**沒有**併進結果卡的「校正 N」chip。

## 5. 總監實測與限制

- 總監按 **App 實際路徑**、個人測試集：錯誤率 **10.3% → 8.4%**（第一版 B 是 8.7%）；Qwen3 是 9.9%；**44 句正常英文 0 句改錯**。
- 限制：**測試句是用字典詞出的題，效果偏樂觀**（研究報告 §7 第 3 點）；**只修字典裡有的英文詞**。

## 6. 留給下一個人的坑

1. **使用者要把常用英文專有名詞加進個人字典**，B 才有東西比。字典沒有的拼錯（GemanieGPT 黏在一起、N8、tmap 太短）修不到。
2. **web2 缺很多常用字**：連 `box`、`has`、`paid`、`internet`、`laptop` 都沒有。我拿約 400 個最常用英文字逐一對照 web2 找出缺的並補進 `_MODERN_ENGLISH_WORDS`。**沒補到的正常字會被當成「不是正常字」而進入模糊比對**——只有「很像某個 ≥5 字元的字典詞」才會被改，風險不大，但看到新的誤換就先想「是不是字表缺這個字」。
3. **句尾緊貼 ASCII 句號的拼錯不會修**（`use clardcode.`）：規則 2 把 `.` 當網址字元。蘋果中文句用全形標點，影響小；要放寬的話得區分「句號」與「網址點」，先量過再動。
4. **Windows／沒有 `/usr/share/dict/words` 的機器 B 整步跳過**（記一次 log_error）。Windows 版若要用，得自帶字表。
5. **「兩個詞一組」我加了一條規格沒寫的限制**：目標必須也是兩個詞的字典詞。否則 `make a Figmar` 的 `a Figmar` 合起來離 Figma 只有 0.29，冠詞 a 會被整組吃掉。代價：`trading view`（兩個詞）不會被換成 `TradingView`（一個詞）。
6. **大小寫修正會動「Vibe Coding」**：vibe 不在字表、coding 靠字尾還原算正常字，所以整組不是「全正常」，正規化後跟字典的 `vibe coding` 相同 → 改成小寫的字典寫法。依規則 4 是對的，但如果使用者想保留標題式大寫，要把字典寫成 `Vibe Coding`。
7. **`_en_boundary_ok`／正常字過濾是「不改錯」的主力**，拿掉任何一條都有測試轉紅（見 §7）。調門檻前先看那些測試。
8. 用個人測試集驗證的方式：用 App 的真實路徑（`Transcriber.transcribe`，帶 `chinese_variant=traditional_tw` 與使用者字典）轉測試集，和稿子逐字比；不要自己呼叫 `_apple_match_english`，會漏掉既有 corrections 與重整。

- 先寫測試（改完測試檔後 115 個失敗，`AttributeError`／行為不符），再實作到全綠。
- 審查兩份「現版改錯」清單的 43 句全部變成回歸測試（每句單獨、夾在中文句裡各測一次，都不能被改）；11 個該換的拼錯（clardcode、gitub、wibecoding、Nervidia、Figmar、Parquite、Wisper、clad sonet、tradingiew、Clawd Code、claud code）全部換對；字表檔不存在／太小 → B 跳過；大小寫修正只對非正常字；網址旁不碰。
- 相關測試檔（`test_v2350`／`test_version`／`test_apple_stt`／`test_apple_stream`／`test_v2340`）：377 passed, 1 xfailed（xfail 不是本版的）。全套結果見最後回報。
- 所有測試用假結果：不開麥克風、不載模型、不呼叫真的 helper、audit 換成假物件。跑測試一律排除 `tests/test_history_canvas.py`（會開真的視窗）。
- Mutation（複製目錄 `scratchpad/v2350_mut`，腳本 `scratchpad/run_mut_v2350b.py`，前景逐個跑、跑完還原）共 24 個：
  - **CAUGHT 23 個**：門檻改回 0.34、拿掉正常字過濾、候選長度下限改 3、拿掉網址防護、拿掉只差數字或 s、大小寫修正對正常字也做、拿掉第二名差距、兩詞一組目標不限兩詞、兩詞皆正常也比對、字表載不到仍繼續比對、字表過小不視為壞檔、er 字尾詞幹下限改 3、拿掉字尾還原、補充字表清空、含中文字典詞也當候選、系統訊息也處理、對 Qwen3 也跑、拿掉 corrections 目標當候選、放到 corrections 之前跑、英文例外不被接住、日誌寫出文字、大小寫修正拿掉、單字不檢查正常字。
  - **NOT CAUGHT 1 個：「單位 < 3 字元閘拿掉」**——這是**等價變異**：單位 ≤ 2 字元時，精確比對要候選也 ≤ 2 字元（但候選本來就要 ≥ 3），模糊比對要候選 ≥ 5 字元（距離至少 3、比例 ≥ 0.6，超過門檻），所以這道閘拿掉不會改變任何輸出。保留它是防禦性寫法（規格要求），沒有測試能、也不需要抓它。
  - 第一輪有 3 個變異是我腳本寫壞（補充字表清空沒真的清空、大小寫修正拿掉造成語法錯誤）或測試太弱（含中文字典詞也當候選：原測試用的拼錯離 Claude 太遠）；改腳本與測試後重跑，全部 CAUGHT。

### 留給下一個人的坑（補）
- 這個功能只修「字典裡的英文詞」。使用者常講的英文產品名要加進字典，才會被修；字典裡的詞越短越不會被拿來模糊比對（< 5 字只做大小寫修正）。
- 每加一條防護，都可能讓某個真的拼錯修不到（Figmar、小寫 tradingview）。改規則時先跑 `tests/test_v2350_apple_postfix.py` 的正常句清單，再用個人測試集量。
- 審查員的探測腳本在暫存區，會被系統清掉；需要時照本節的例子重建。
