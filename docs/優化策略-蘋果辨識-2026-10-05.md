## 0. 一句話結論

**蘋果辨識本身已經很快（約 0.45 秒），使用者等的 1.16 秒裡有六成花在辨識以外。**
最大的速度改進是「錄音當下就邊錄邊餵給一個常駐的蘋果引擎」；最大的準確度問題是
**手上沒有任何真人錄音的標準答案**，所以準確度要先「量得到」才能「改得準」。
另有一個確定的正確性 bug（重複數字被吃掉）要先修。

## 2. 主對話親手做的蘋果引擎實驗

所有實驗都用 `say -v Meijia` 合成語音（**不能代表真人準確度**，只看方向與機制）。

### 2.1 「聽寫引擎」比「一般引擎」中文好，但會吃掉英文

| 測試句 | 一般引擎（現在用的） | 聽寫引擎＋標點 |
|---|---|---|
| 幫我算一下紫微斗數的命盤 | ✗ 子為鬥樹 | ✓ 紫微斗數 |
| 這個系統的複雜度只有前面那個的一半 | ✗ 係統、復雜、隻有、前麵（事後修） | ✓ 引擎本身就寫對 |
| 我現在搞不清楚該用 Opus 還是 Fable 比較好 | 大致聽到（Oppus、fable） | **✗ 英文整個不見**：「該用還是」 |
| 它的大小只有 Qwen3 的一半 | ✗ Quan三 | **✗ 英文不見**：「只有三」 |

聽寫引擎有 `.punctuation` 選項（v2.31.0 當時沒發現，以為它沒標點），但加了標點也只補逗號、句尾不加句號。
「吃掉英文」可能是合成語音的英文發音太差造成——**一定要用真人聲音驗證**。

### 2.2 兩個引擎同一次跑，幾乎不多花時間

把兩個模組放進同一個 `SpeechAnalyzer`：3 句合成語音各 279／291／453 ms，跟只跑一個差不多。
→「兩個都跑、挑好的那個」成本可行。

### 2.3 自訂語言模型（教引擎認專有名詞）：無效，停止

蘋果有官方的 `SFCustomLanguageModelData` → `SFSpeechLanguageModel.prepareCustomLanguageModel`
→ `DictationTranscriber.ContentHint.customizedLanguage`。實測：

- 中文**可以建**：使用者字典 199 個詞，約 1 秒編好（4.4 MB），中文發音規則 708 個音素
- **完全沒有效果**：「叡揚」一律寫成「瑞陽」。試過：只給詞彙、加上下文句型（「我在X上班」等）、
  權重 0.3／0.7／1.0、改用聽寫引擎的 contextualStrings
- 推斷：「叡」可能不在蘋果的中文字庫裡，要用 `CustomPronunciation` 教發音，但發音編碼（`a_5`、`u_4` 這類）
  沒有公開對照表，只能猜——不值得
- 專有名詞目前靠既有的換字規則（`瑞陽→叡揚` 已存在），這條路有效

### 2.4 沒有真人錄音可以拿來比

App 為了隱私不存錄音（`suspicious_audio_capture = False`），唯一一個保存的檔是 5 月的 1 秒雜音。
T02（建立真人準確度尺）至今仍卡在「使用者沒錄素材」。

## 3. 審查找到的問題（依類別）

### 3.1 正確性 bug（確定，主對話親自驗過）

**重複數字被吃掉**：`_dedupe_repetitive_ngrams`（`transcriber.py:928`），所有後端都會跑

| 輸入 | 輸出 |
|---|---|
| 驗證碼是000000 | 驗證碼是00 |
| 電話0912121212 | 電話0912 |
| 金額888888元 | 金額88元 |
| 哈哈哈哈哈哈 | 哈哈 |

真實紀錄目前 0 次命中，但使用者明確在做數字聽寫（v2.31.3），是靜默改壞資料、不會有任何提示。

### 3.2 速度

|---|---|---|---|
| S1 | 蘋果沒用原生串流：自己每 10～12 秒切一段、每段重開一次 Swift 程式，放開後才轉最後一段 | 38 場開了 337 次程式；9.4% 的切點找不到停頓、硬切在句子中間 | 審查原型（常駐＋邊錄邊餵，合成語音）：放開後辨識 **468 → 約 120 ms**；硬切與接縫消失 |
| S2 | 關鍵路徑順序：先畫畫面、寫資料庫，最後才貼上；先畫卡片，才起辨識 | `gui.py:2584-2693`、`3435→3458→3541` | 約 **−290 ms**（推斷） |

- 蘋果的轉錄紀錄 `backend` 欄位寫成 `mlx`（`transcriber.py:1238` 印的是常數），統計會分錯組

- 啟動時間 9/30 起從約 4 秒變 13 秒，期間沒有程式改動，推斷是系統記憶體壓力（swap 5.5/6.1 GB），R3 可以緩解

## 4. 建議計畫（分三階段）

### 第一階段：快速修正（低風險、改動小）

| 項目 | 效果 |
|---|---|
| A1 重複數字不再被吃掉 | 正確性 |
| R2 切到蘋果時卸載 Qwen3 | −3.6～6.3 GB |
| R4 拿掉已廢案的量測 | 每次 −35 ms |
| R1 視窗不在前景時降低重畫頻率 | 閒置 CPU 約 25% → 5～10% |
| R5 熱鍵看門狗不要每 5 秒寫一行 | 日誌可回溯天數 ×7 |
| S2 先貼上、再畫畫面寫資料庫 | 約 −0.1～0.3 秒 |
| 3.5 的 backend 欄位 | 統計正確 |

### 第二階段：蘋果常駐串流引擎（最大的速度改進）

- Swift helper 加「常駐模式」：錄音一開始就建好引擎，錄音期間每 0.1 秒把聲音餵進去
- 同一個引擎**同時跑一般與聽寫兩個模組**（2.2 實測幾乎不多花時間），兩份結果都寫進紀錄——
  這就是第三階段要用的「影子資料」，使用者看到的仍是一般引擎的結果
- 放開熱鍵後只剩引擎收尾（原型約 120 ms）；不再切段、不再接縫、不再每段開程式
- 現有「整檔送」路徑保留當備援
- 預期：使用者等待中位數 1.16 秒 → **約 0.4～0.6 秒**（推斷，搭配第一階段 S2）

### 第三階段：用真實資料決定準確度策略（第二階段跑一週後）

- 比對一週的影子資料：兩個引擎在哪裡不一樣、英文是否真的被吃、哪一個的中文比較對
- 依結果決定路由（例如：有英文用一般引擎、純中文用聽寫引擎），或用信心值把少數片段交給 Qwen3
- 同時：S3 尾音等待改成「偵測到安靜就不等」

## 5. 刻意不做的

- **自訂語言模型**：兩輪實驗無效（2.3），不再投入
- **用蘋果的 SpeechDetector 取代 Silero**：審查原型單獨跑會當掉、同跑時 0 筆偵測，不可行
- **Silero 改 ONNX 版**（省 87 MB）：要自己重寫切段函式，而 v2.31.3 的數字修補依賴它的切段結果，風險不划算；
  延後到 R3 其他部分做完再評估

---

## 6. 不確定、待查

- 所有蘋果延遲與準確度實驗都是合成語音；常駐串流對 10 分鐘以上長錄音的穩定性沒測
- 關麥克風卡 15 秒的根因
- 閒置 CPU 的機制（整張底圖跟著重畫）是隔離實驗推斷，真 App 沒有剖析工具可確認
- 尾音等待縮短會不會切掉尾字
