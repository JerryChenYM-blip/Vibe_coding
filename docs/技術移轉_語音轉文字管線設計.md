# 技術移轉：本地語音轉文字管線的設計與心法

> **這份文件要回答的問題**：兩個團隊用同一個 ASR 模型，為什麼辨識效果差很多？
>
> **答案的一句話版本**：因為模型只是整條管線裡的**一格**。這份文件拆解它前後的十幾層處理，
> 以及每一層是被什麼真實事故逼出來的。
>
> 文件裡所有數字都標註來源。**引用他人的數字會明講是引用**；沒有實測依據的一律標「待查」，
> 不用推論冒充實測。

## 0. 先看全貌：模型只佔中間那一格

```

│  │  在「停頓處」切塊（不是每 N 秒硬切）│                        │
```

## 1. 最可能造成落差的三件事（先講結論）

### 1-1 固定時間切塊 = 每 N 秒把一句話腰斬一次

長錄音必須切段處理。多數實作是「每滿 10 秒切一段」。

**這個做法的代價，本專案量過**（原始碼註解原文）：

> 「fixed_chunk streaming 每滿 10s 就硬切一段送轉錄，切點與語意無關
> （**實測 195 個接縫 100% 落在句中**）。」

100%。不是大部分，是全部。等於每 10 秒把一個詞剖成兩半，兩半分別送進模型——
**模型再好也救不回來，因為它拿到的本來就是半個詞。**

**解法**：在切之前，先往回找一段「真正的停頓」，把切點挪過去。

實際演算法（RMS 法，刻意不跑完整神經 VAD——每秒都要判斷，太重不划算）：

```
1. 把緩衝區尾端切成 80ms 小視窗，各算能量（RMS）
2. floor = 這段音訊裡最安靜的值   ← 這段自己的「噪音底」
   hi    = 中位數                ← 這段自己的「講話音量」
3. 動態範圍檢查：hi / floor < 1.6 → 整段音量太平
   （要嘛全程吵、要嘛全程都在講）→ 放棄，不冒險切
4. 門檻 = floor + 0.3 × (hi − floor)
5. 持續性檢查：連續 ≥3 個視窗（240ms）都低於門檻才算真停頓
   → 濾掉音節之間的短促凹陷
6. 在合格區段裡取最安靜的那一點當切點
7. 找不到 → 回報「沒找到」，讓上層決定再等或硬切保底
```

**第 4 步的公式是這整套的核心，而且它是第二版**。第一版失敗得很徹底：

> 「舊公式 threshold = median × 0.3 要求 SNR > 3.33 才可能成立；背景噪音把停頓的
> 音量墊高時，**數學上永遠達不到** → 實測 7/20、7/23 兩天 **0/18 全撞 hard cap**、
> 7/24（安靜）7/7 全中，**整體只有 28%**。錨點（median）從來就不代表『噪音底』。」

看懂這句話就懂了整個關鍵：**門檻要錨在「這段音訊自己的噪音底」，不是錨在音量中位數、
更不是一個絕對值。** 在吵雜環境裡，「停頓」的絕對音量可能比安靜環境裡的「說話」還大。

改公式後（合成音訊模擬驗證）：

> 「SNR 1.2–20 × 停頓 300–1200ms 的組合，**SNR ≥ 1.5 找到停頓率 100%**
> （舊演算法 SNR ≤ 3 為 0%），且『連續講話沒停頓』的誤切率維持 0%。」

**還有第三版**，改的不是公式而是「看得到多遠」：

> 「實測 206 筆切窗、所有命中切點都 ≥7.64s（理論下限 10s 觸發 − 2.5s 窗 = 7.5s 幾乎
> 完全吻合）——演算法只看得到每個 12s 週期的**最後 37.5%**、前段的自然停頓根本沒機會
> 被檢查，**這是命中率卡在 41.5% 的結構主因**。拉到 4s 讓可視範圍擴到 6–12s。」

**這一步的教訓值得單獨拿出來講**：命中率卡住的原因不是「演算法不夠聰明」，
而是「**演算法根本沒被給機會看到那段音訊**」。調參數之前先確認你的方法看得到全部資料。

> ⚠️ **誠實標註**：搜尋窗拉到 4.0s 之後的真實命中率，原始碼註解裡**沒有記錄**。
> 本專案後續從 log 撈出的 11 天樣本顯示約 53%（近 7 天 67%），但那批樣本混入了
> 開發測試事件、無法乾淨分離，**這個數字要帶保留看**。

### 1-2 詞表注入的「格式」，比「有沒有注入」更關鍵

把使用者的專有名詞餵給模型當先驗，這件事不難想到。**真正的差異在怎麼包裝那串詞。**

第一版照官方範例用空白分隔的裸詞表（`交易 停滞`）。結果：

> 「實機 log 發現靜音／雜音段時模型會把這串 bare list 當成『**剛剛轉錄完的句子**』
> 續寫——直接把字典詞當答案吐出來（真實 case：
> 『Qwen3-ASR Qwen3 Qwen Large V3 Turbo Whisper Pro Ollama Claude Cloud
> ChatGPT Cursor GitHub』）。」

使用者只是講了一段話，App 回吐一串產品名稱。

**修法是加一層「框」**：

```
❌  交易 停滞 潤飾 辨識            ← 模型讀成「待續寫的文本」
✅  專有名詞：交易、停滯、潤飾、辨識。  ← 模型讀成「參考清單」
```

加了語意前綴（「專有名詞：」）、頓號分隔、句號收尾之後，模型才分得清
「這是參考資料」還是「這是我該說的話」。

> 📎 **來源標註**：原始碼註解引用了一個同類技術的外部實測「TypeWhisper 184-run：
> WER 33.8% → 18.2%」。**那是引用他人的 benchmark，不是本專案自己量的數字**，
> 引用時請照樣標明。

**更重要的是這件事的第二層**：注入先驗**會製造一個新的失敗模式**（模型吐詞表），
所以必須再寫一個專門的偵測器去抓它。這是一個閉環：

```
加分機制（注入先驗）→ 產生新缺陷（詞表被吐回）→ 需要專屬偵測器（見 3-1）
```

**不踩過這個坑，不會知道要防它。** 這是這份文件最想傳遞的一種知識。

### 1-3 三層閘門的門檻，全部由實機資料校準

「什麼時候不要把音訊送進模型」——這層擋掉的不只是浪費的運算，
更重要的是**擋掉幻覺**：空白或純噪音的音訊送進模型，它常會編出內容。

| 層 | 判斷 | 門檻 | 為什麼是這個數字 |
|---|---|---|---|
| 1 | 太短 | **≤ 0.4 秒** | 誤觸熱鍵、或切塊後殘留的小片段。註解：「是字典 dump／假新詞／重複病三隻幻覺的高發地帶」 |
| 2 | 能量太低 | **RMS < 0.004** | **從 0.002 收緊來的**——見下方 |
| 3 | 不是人聲 | 神經 VAD **閾值 0.35** | RMS 分不出打字聲/冷氣聲跟人聲 |

**第 2 層那個數字的來歷，是這份文件最值得抄的一種「工作方式」**：

> 「v2.19.0：0.002 → 0.004（從 -54 dBFS 收緊到 -48 dBFS）。原因：實機 log 看到
> 0.002 漏掉『peak ~0.005 純底噪』案例，這類音檔被送進模型後觸發字典 dump。」

不是查論文、不是憑經驗猜，是**線上出包之後回頭調的**。

**而第 3 層有一個刻意的「放水」設計，方向性比數值更重要**：

> 「長音逃生門——音檔 > 4s 即使 VAD 回 no_voice 也照送。實測 21 筆被擋的音長
> [0.4..3.6, 4.4, 4.4, 5.4]，其中 5.4s（普通話可講 ~38 字）**極可能是真語音被誤殺**
> （VAD 對小聲／口音／遠場偶爾誤判）。長音被當『純雜音』的機率極低、
> **誤殺成本遠高於放水**。」

**心法：每一層過濾都要先想清楚「往哪個方向失敗比較不痛」。**
這裡選的是「寧可多跑一次推論，也不要吃掉使用者的話」。

## 2. 送進模型之前的其他處理

### 2-1 錄音格式：直接錄 16kHz 單聲道

模型內部就是 16kHz 單聲道。錄音端直接用這個規格，省掉「錄 48kHz 立體聲再降頻」
那段轉換與失真。格式用 float32 [-1,1]，音訊層與模型兩邊都認得，中間不做整數↔浮點轉換。

### 2-2 尾音補償：放開按鍵後再多錄 300ms

```python
TAIL_PADDING_MS = 300
# 使用者放開熱鍵 → 不立刻停 → 300ms 後才真的停
```

人講完最後一個字到手指放開按鍵之間有生理延遲。不補這 300ms，
**最後一兩個字會被切掉**。純物理緩衝，不做任何判斷。

**這是投資報酬率最高的一項**：一行延遲呼叫，使用者立刻有感。
建議當作驗證這份文件能不能對接你們架構的第一個試金石。

### 2-3 音量正規化：拉起來，但要有煞車

小聲說話會被閘門誤判成靜音整段丟掉，所以峰值太小要拉起來。
**但不能無腦拉滿**，兩道煞車：

```python
if peak <= 0.005:  跳過      # 這種等級是純底噪，拉滿只會把噪音放大成假人聲
scale = min(0.9 / peak, 12.0) # 放大倍率上限 12 倍
```

第一道是關鍵：**把底噪放大到「聽起來像人聲」，反而會誘發幻覺。**

### 2-4 切塊的三個門檻不是同一件事

```
累積 10 秒  → 開始「考慮」切一段（切多長交給停頓偵測決定）
錄音 < 12 秒 → 完全不啟動切塊（切塊有派工成本，短錄音不划算）
硬切上限 12 秒 → 一直找不到停頓時，最晚在這裡強制切
```

三個數字語意完全不同，只是恰好其中兩個都是 12 秒。
**合併成一個常數會失去獨立調整的彈性。**

### 2-5 分段並行的兩個防護

**順序保護（index-based slot）**：派工前先在主執行緒同步佔一個位置拿到編號，
背景執行完直接寫回那個位置。每個位置只有一個寫入者，不用鎖也不會錯位——
就算第 3 段比第 2 段早跑完，順序也是對的。

**世代保護（generation guard）**：每次新錄音把世代號 +1。背景執行緒完成時
先檢查世代號還是不是自己出發時那個，不是就丟棄結果。

> 防的是：上一段錄音還有背景工作在跑，使用者已經開始下一段——
> 舊結果會污染新錄音的逐字稿。**這個 bug 只在快速連續錄音時出現，很難重現。**

## 3. 模型輸出之後的濾網

**順序本身是設計過的**，不是隨便排：

```
詞表污染偵測 → 幻覺過濾 → 已知錯字修正 → 局部去重 → 接縫縫合 → 簡繁/在地用語
```

其中一個順序的理由很典型：

> 「去重要放在錯字修正**之後**跑——修完詞才測重複；否則『Cloud Cloud Cloud』
> 會先被砍成『Cloud』、錯字修正才有機會修『Cloud → Claude』。」

順序反了，兩層都白做。

### 3-1 詞表污染偵測（先驗注入的代價）

**雙層判定**：

1. **框的前綴是鐵證**：輸出開頭若是「專有名詞」四個字 → 100% 判定，
   不需要看其他條件。沒有人會口述「專有名詞：」再列一串詞。
2. **字元覆蓋率**：算輸出有多少比例的字落在「詞表所有字的聯集」裡，
   **≥ 0.85** 且至少 5 個完整詞出現才判定。

第 2 條的門檻**曾經因為詞表變大而失效過一次**：

> 「原本只去空白／換行，但框的『、。：』會被算進分母、把 dump 的覆蓋率
> 從真實 ~96% **稀釋到 80.5% < 門檻 → 漏網**（詞表加到 48 詞後復現的 regression）。」

**心法：字典規模是這個判定的隱藏變數。** 擴充詞表時要連動重驗幻覺偵測門檻，
不能只當成「加詞」這一件事。

還有一道**純物理**的第二保險：音檔 < 2.5 秒卻吐出超過「秒數 × 10」個字
（普通話最快約 7 字/秒），且命中 ≥5 個詞表詞 → 直接判定污染。
這條不靠覆蓋率、不靠字典大小，靠「物理上不可能」。

### 3-2 幻覺過濾：兩種形態分開處理

| 形態 | 判斷 | 動作 |
|---|---|---|
| **卡迴圈** | 同一個 2–6 字片段重複 ≥8 次、佔全文 ≥80% | 整段砍 |
| **訓練資料殘留** | 短句（< 20 字）比對已知幻覺語句清單（訂閱語、字幕組署名…） | 整段砍 |
| **局部重複** | 2–5 字片段連續重複 ≥3 次 | **只砍重複的部分**，保留句子其他部分 |

三個刻意的設計：
- **20 字以上的長句免檢**——幾乎不會有 20 字以上的純幻覺
- **局部去重不試「單字」重複**——會把「好好好」這種正常語氣強調誤砍
- **至少 3 次才算重複**——2 次可能是合法強調

**優先逐段過濾、沒有分段資訊才整段判斷**：一句話裡一段是幻覺、其他段是真的，
不該整句被砍光。

### 3-3 接縫假標點

即使切點抓在停頓處，各段獨立送模型後，模型仍會**各自在段落結尾補一個句號**——
對「被切開的半句」而言那是假的。

> 「實測 162 組多段錄音、**14/14 接縫的句號都是假的**，甚至把『三千六』切成
> 『月三。千六』、把『辦法』切成『辦。法』、把『如果我每個月』切成『果我。每個月』。」

**修法**：除了最後一段以外，每段結尾若是句末標點就移除再拼接；
**段落內部的句號保留**（那是模型真正偵測到的停頓）。

### 3-4 在地用語否決層：轉換工具會自作主張

簡繁轉換工具（OpenCC 的 `s2twp`）不只轉字，還會做「地區詞彙替換」，
而它的替換規則是通用語料訓練的，不一定貼合你的使用者。

真實案例：

> 「轉換工具把使用者口述的『優化』自作主張轉成『最佳化』。實測 9098 筆 log：
> 『最佳化』出現 11 次、『優化』**0 次 = 100% 被轉掉**、使用者從沒成功輸出過『優化』。」

**修法是加一層否決層**把它轉回來，但要保護合法邊界
（「最佳化身」「最佳化學」是「最佳 + 化X」，不能動）。

而這條否決規則本身**做過影子驗證才上線**：

> 「555 筆真實 log 中『最佳化』12 處全是動詞、後接字無一個是身/學/妝，**零誤傷**。」

## 4. 「做了又拿掉」的機制 —— 負面知識

**這一節可能是整份文件最值錢的部分。** 因為別人不會知道這條路是死路，會自己再走一次。

### 4-1 拼音模糊比對：聽起來很聰明，實際被停用

**構想**：中文 ASR 的同音字錯誤（「潤飾」→「論視／潤世／潤示」）**無法窮舉成規則**，
因為錯誤的字面組合是開放集合。所以改用「拼音編輯距離 ≤ 門檻就替換」的模糊比對。

**實作得相當謹慎**：只索引純中文、只索引 ≥2 字的詞、拼音長度 ≥4 才收錄、
字元長度必須完全相同才比對、還加了逐字同音率的錨定檢查。

**結果**：

> 「上線後 230 筆稽核 log 發現 sliding window + pinyin match **沒有詞邊界概念**、
> 會把『已經準備』的子字串『經準』誤配詞表裡的『精準』→ 改成『已精準備』。
> **真實使用 1 命中 / 230 筆全是誤傷。**」

**根因**：滑動視窗會從「已**經準**備」裡切出「經準」——這個子字串**跨越了兩個詞的邊界**
（「已經」+「準備」），而它的拼音（jīngzhǔn）跟「精準」完全相同。

**訊噪比是負的，所以整個關掉，而不是調參數。**

要重新啟用，得先補「易混淆詞白名單」或接一個中文斷詞器提供詞邊界保護。

### 4-2 同一類坑，在另一個地方也踩到

繁簡殘留字清理如果做成**單字**替換（「隻」→「只」），
會把「一**隻**美股」誤改成「一只美股」（那個「隻」是量詞）。

所以那層立了一條鐵律：**只做長度 ≥2、上下文無歧義的詞組替換，禁止單字替換。**

**共同教訓：任何子字串／單字級別的替換，脫離上下文就會啃到不該啃的邊界。**

## 5. 模型保溫：冷啟動的真實代價

**問題**：GPU 的著色器（shader）沒被編譯過時，第一次推論非常慢。

> 「warmup 完成後立刻錄 1.6s 音檔，推論花 **12 秒（比即時慢 7.5 倍）**；
> 之後同樣大小的音檔降到 **0.2 秒**。」

**60 倍差距。** 使用者第一次用就等 12 秒，很可能就不用了。

**解法有兩個層次，而且第一個直覺是錯的**：

**❌ 用靜音暖機沒有用**——模型內建的 VAD 會直接跳過靜音，著色器根本沒被編譯到。

**✅ 要合成一段「假人聲」**：
```
150Hz 基頻 + 800/1500/2500Hz 三個共振峰（模擬中文母音頻段）
+ 5Hz 振幅調變（模擬音節節奏）
+ 振幅壓到 0.05（人耳幾乎聽不到）
```

第一版用純 440Hz 正弦波，後來換成上述多共振峰合成音，因為
「純正弦波的頻譜特徵不夠廣，需要更接近真實語音」。

**第二層是記憶體釘選**（作業系統層）：

> 「把模型權重釘在實體記憶體、不被作業系統換出。這才是『閒置後冷載入 12–16s』的
> 對症 API：舊版用的另一個 API 管的是『可回收暫存池』、跟權重常駐量是**兩個計數器**，
> 防不了換出（稽核實證：8941 筆 ping 顯示權重駐留量與暫存池上限完全脫鉤）。」

**這裡有個順帶的教訓**：曾經因為把「權重常駐量」誤標成「暫存池」，
導致一次修正「看起來沒生效」，其實是**量錯了東西**。
修 bug 之前先確認你量的是不是會痛的那個指標。

## 6. 貫穿全部的方法論：加一個機制之前先做什麼

拼音守衛翻車之後，這個專案立了一條硬性紀律：

> **任何新的字串／模糊比對規則，上線前必須先在全量真實語料上回放，
> 算出「會修正幾筆」與「會誤傷幾筆」。誤傷 > 0 就不上線，或改成錨定規則。**

實際操作的樣子（一個真實例子）：

```
候選規則：「跟正」→「更正」
全語料掃描：6 筆命中
逐一判讀：5 筆確實是「更正」的誤聽
          1 筆是「以最高效率跟正確性完成」← 合法！「跟」+「正確性」
結論：不能做成全域取代
改成錨定：「跟正，」「跟正一下」「跟正它」「跟正的」四條
回放驗證：修正 5 筆、誤傷 0 筆 ✅
```

**沒有這一步，你會做出一條把「已經準備」改成「已精準備」的規則，
而且要等到使用者抱怨才知道。**

同樣的紀律也適用於「量測」本身：

> **實驗被汙染就整輪作廢。** 本專案有一次差點根據「八成錄音短於 10 秒」下結論
> 「切塊優化不值得做」，後來發現那個時長欄位對長錄音是壞的（50.3% 的紀錄
> 秒數與字數在物理上不可能）。**建立在髒資料上的結論，比沒有結論更糟。**

## 7. ⚠️ 哪些不能直接照抄

| 內容 | 綁定於 | 換到別的環境要怎麼辦 |
|---|---|---|
| 記憶體釘選、GPU 著色器暖機 | **Apple 晶片 + Metal** | 概念可移植（防止權重被換出、預熱運算核心），但 API 完全不同。CUDA / CPU 環境的冷啟動特性也不一樣，**要重新量而不是照抄數字** |
| 簡繁轉換、在地用語否決層 | **中文（且是台灣用語）** | 其他語言沒有這個問題；但「轉換工具會自作主張改詞」這個**現象**在任何做在地化的地方都可能出現 |
| 拼音模糊比對 | **中文** | 其他語言要換成對應的語音相似度（例如英文的 Soundex / Metaphone），**而且會踩到同一個詞邊界坑** |
| 所有門檻數值（0.004 / 0.35 / 0.85 / 1.6 / 0.3…） | **這個使用者的麥克風、環境、口音** | **一律要用自己的真實資料重新校準**。照抄數字是這份文件最容易被誤用的地方——重要的是「用什麼方法決定這個數字」，不是數字本身 |
| 詞表上限 30 / 50 | 工程判斷值 | 原始碼裡**沒有**精確的推導依據，是經驗值。你們的模型上下文長度不同就要重新試 |
| 8 分鐘 / 15 分鐘看門狗 | 這個使用者的使用型態 | 概念（防止忘記關錄音）通用，數值要看你們的典型錄音長度 |

**可以直接搬的（與平台、語言都無關）**：

- 在停頓處切塊、而不是固定時間硬切 —— **這條最值得搬**
- 分段接縫的假標點移除
- 尾音補償
- 詞表注入要加語意框
- 三層閘門的「疊加 + 保守失敗方向」設計
- 上線前用真實語料回放驗證誤傷的紀律

## 8. 如果只能做三件事

1. **把固定時間切塊換成停頓對齊切塊。**
   這是唯一有「改前 vs 改後」實測對比、而且直接對症「同模型效果較差」的機制。
   固定切塊「195 個接縫 100% 落在句中」——換算成人話就是每 10 秒把一句話腰斬一次。
   比換模型的投報率高得多。而且門檻公式的失敗經驗（錨在中位數 → 數學上永遠達不到）
   已經幫你踩過了。

2. **詞表注入加語意框，並且同時做污染偵測。**
   格式從裸詞表改成「專有名詞：A、B、C。」；同時準備好偵測「模型把詞表吐回來」，
   因為那是這個加分機制必然的副作用。

3. **建立「新規則先回放驗證」的紀律。**
   這不是演算法是流程，但它是前兩項能持續有效的前提。
   這個專案所有能講出「修正 N 筆、誤傷 0 筆」的機制，都是因為有這一步；
   唯一沒做這一步就上線的機制（拼音守衛），是唯一被整個關掉的。
